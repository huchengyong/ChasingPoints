## ADDED Requirements

### Requirement: 匹配码携带映射到签名 token 的短码
获取匹配二维码时，服务端 SHALL 在签发签名 token 的同时生成一个新的短码，并把短码到 token 的映射写入 Redis，有效期等于该 token 的剩余有效期。`qrcode_data` SHALL 为携带该短码的匹配码入口链接；`invite_token` 与 `expires_in_seconds` 的语义保持不变。短码 MUST 具有不少于 64 位的随机熵，且只使用 URL 安全字符。短码映射写入失败时，接口 MUST 返回失败，不得返回无法兑换的匹配码。签名 token 的格式、签名校验与开局校验规则 MUST 保持不变。

#### Scenario: 签发匹配码
- **WHEN** 已登录且账号正常的用户获取匹配二维码
- **THEN** 响应 SHALL 返回 `https://www.zhuifen.cn/go/?j=<短码>` 形式的 `qrcode_data`
- **AND** 该短码 SHALL 能在 token 有效期内兑换回同一个 token

#### Scenario: 刷新匹配码
- **WHEN** 同一用户在旧匹配码过期前再次获取匹配二维码
- **THEN** 服务端 SHALL 生成新的短码
- **AND** 旧短码 SHALL 在其自身有效期内继续可用，与旧 token 的行为一致

#### Scenario: 短码过期
- **WHEN** 短码对应的 token 已过有效期
- **THEN** 该短码 MUST 无法兑换或预览

#### Scenario: 映射写入失败
- **WHEN** 写入 Redis 失败
- **THEN** 接口 SHALL 返回 `success: false`，不返回二维码内容

### Requirement: 未登录可凭短码预览邀请
系统 SHALL 提供匿名的匹配码预览接口，凭短码返回邀请人的昵称、头像与过期时间。响应 MUST NOT 包含签名 token 或邀请人的用户 ID。短码不存在、已过期、对应 token 校验失败或邀请人账号不可用时，接口 SHALL 统一返回失败与「匹配二维码已失效，请让对方刷新二维码」，不得区分这几种原因。接口 SHALL 在查询 Redis 前校验短码格式，并 MUST 按客户端 IP 限制请求频率；超出限制时返回失败与「操作太频繁，请稍后再试」。

#### Scenario: 有效短码
- **WHEN** 未登录的请求用有效短码调用匿名预览接口
- **THEN** 响应 SHALL 返回邀请人昵称、头像和过期时间
- **AND** 响应 MUST NOT 包含 token 或邀请人用户 ID

#### Scenario: 无效或过期短码
- **WHEN** 请求使用不存在、已过期或格式不合法的短码
- **THEN** 响应 SHALL 返回失败与统一的失效提示

#### Scenario: 邀请人账号已停用
- **WHEN** 短码有效，但邀请人账号已被禁用或注销
- **THEN** 响应 SHALL 返回失败与统一的失效提示

#### Scenario: 请求过于频繁
- **WHEN** 同一 IP 在限流窗口内的请求次数超过上限
- **THEN** 后续请求 SHALL 直接返回失败与频率提示，且 MUST NOT 查询 Redis 中的短码映射

### Requirement: 登录后用短码兑换 token
系统 SHALL 提供需要登录的短码兑换接口，返回该短码对应的签名 token 和预览信息。预览信息与现有匹配邀请预览一致（邀请人 ID、昵称、头像、过期时间），校验规则也与现有预览一致。兑换 MUST NOT 消耗短码或 token；开局仍由现有开局接口凭 token 校验。

#### Scenario: 兑换有效短码
- **WHEN** 已登录用户用有效短码调用兑换接口
- **THEN** 响应 SHALL 返回 token 与邀请人 ID、昵称、头像、过期时间

#### Scenario: 未登录调用
- **WHEN** 未带有效登录态的请求调用兑换接口
- **THEN** 系统 SHALL 返回 HTTP 401

#### Scenario: 兑换失效短码
- **WHEN** 已登录用户用已过期的短码调用兑换接口
- **THEN** 响应 SHALL 返回失败与统一的失效提示

### Requirement: 承接页先预览后登录，登录后自动进入确认页
承接页收到匹配码链接后 SHALL 按以下流程处理：
- 未登录：调用匿名预览，展示邀请人头像、昵称、剩余有效时间和「登录并开局」按钮；点击后进入现有登录页。
- 从登录页返回且已登录，或进入时已登录：调用兑换接口，把 token、邀请人信息交给现有确认页 `scanConfirm`，并以替换当前页的方式进入确认页。
- 任一步骤得到失效结果：展示失效状态与「返回首页」按钮。

承接页 MUST 只在内存中持有短码与 token；交接 MUST 复用现有扫码交接机制，确认页的身份校验与开局规则保持不变。

#### Scenario: 新用户扫码
- **WHEN** 未登录的新用户用微信扫描匹配码并打开承接页
- **THEN** 承接页 SHALL 先展示邀请人的头像和昵称，不立即要求登录

#### Scenario: 登录后继续
- **WHEN** 新用户在承接页点击「登录并开局」并完成登录返回
- **THEN** 承接页 SHALL 自动兑换短码并进入确认页，确认页显示该邀请人为对手

#### Scenario: 已登录用户扫码
- **WHEN** 已登录用户用微信扫描匹配码
- **THEN** 承接页 SHALL 不展示登录按钮，直接兑换短码并进入确认页

#### Scenario: 登录期间匹配码过期
- **WHEN** 用户完成登录返回时短码已过期
- **THEN** 承接页 SHALL 展示失效状态，提示让对方刷新二维码后重新扫码

#### Scenario: 放弃登录
- **WHEN** 用户进入登录页后未登录就返回
- **THEN** 承接页 SHALL 继续展示邀请预览和「登录并开局」按钮

### Requirement: 端内扫码兼容链接码与裸 token
追分小程序与鸿蒙 App 的端内扫码 SHALL 识别以下内容：
- 匹配码链接：取出短码，调用兑换接口，之后与现有扫码开局流程一致，包括「再来一局」只接受原对手匹配码的规则。
- 裸 token：沿用现有预览流程。
- 对局链接：进入该对局的观战详情。
- 裁判码：沿用现有裁判流程，不受影响。

其他链接与内容 SHALL 提示「无效的二维码」。

#### Scenario: 端内扫描匹配码链接
- **WHEN** 已登录用户在端内扫描匹配码链接
- **THEN** 系统 SHALL 兑换短码并进入确认页

#### Scenario: 再来一局扫到其他人的匹配码链接
- **WHEN** 用户从赛果页「再来一局」扫码，扫到的匹配码链接兑换出的邀请人不是原对手
- **THEN** 系统 SHALL 提示「请扫描指定对手的匹配码」，不进入确认页

#### Scenario: 端内扫描裸 token
- **WHEN** 端内扫描内容是现有格式的裸 token
- **THEN** 系统 SHALL 按现有预览流程处理

#### Scenario: 端内扫描海报上的对局链接
- **WHEN** 端内扫描对局链接
- **THEN** 系统 SHALL 进入该对局的观战详情

#### Scenario: 扫描其他网址
- **WHEN** 端内扫描的内容是非入口链接的网址
- **THEN** 系统 SHALL 提示「无效的二维码」
