## Context

九球追分当前的写入方式（本变更不改）：

- 普胜 / 小金 / 大金：`POST /api/match/end-round`，写一条 `match_rounds`（`win_type`，比分列存记分后的累计总分）和一条 `win` 动作（`score_change` 为 4 / 7 / 10，`extra_data.win_type`）。
- 犯规：`POST /api/match/foul`，只写一条 `foul` 动作（`actor` 为犯规方，`score_change=1`，`round_no` 为"已有局数 + 1"），不写局记录。
- 总分累加在 `matches.my_score / opponent_score`。

所以 `match_rounds` 对九球追分只是"胜局事件"的索引，真正完整的事实在有效动作日志里。读取侧却都以局记录为主线：详情页的"局记录"、`total_rounds / current_round`、复盘的逐局切片。最后一次胜局之后的犯规没有对应局记录，按局遍历时会漏掉。

约束：

- 后端读取保持纯读、查询有界、SQL 数量固定（`backend/AGENTS.md`）。
- 公开详情的缓存不得包含查看者个性化数据。
- 复盘的现有口径由未归档变更 `revamp-vip-benefits` 定义，其实现已在代码中。
- UniApp 只面向微信小程序与鸿蒙；原生 iOS 后续迁移。

## Goals / Non-Goals

**Goals:**

- 九球追分的一场对局，能看到双方总分以及普胜、小金、大金、犯规的次数和得分明细。
- 所有统计来自同一个构建函数，详情、结算、复盘口径一致。
- 九球追分的界面不再出现"局数""第 N 局"。

**Non-Goals:**

- 不改表结构、记分接口、撤销、排位结算、成就与称号统计。
- 不改信誉检测规则里九球追分的 `min_total_rounds`（它按胜局次数计，语义可接受）。
- 不改其他球种的展示。
- 不做原生 iOS、管理后台的得分构成展示。
- 不新增跨场次的生涯统计（例如累计犯规数）。

## Decisions

### 1. 以动作日志为统计来源，局记录只用于补胜法

得分构成按有效动作（未撤销）的 id 顺序遍历：

- `win`：得分方为 `actor`，分值为 `score_change`；胜法优先取 `extra_data.win_type`，缺失时取同 `round_no` 局记录的 `win_type`。
- `foul`：犯规方为 `actor`，得分方为对方，分值为 `score_change`。
- `score`（2026-10-13 之前九球追分允许通过 `/score` 直接加分，现已禁止）：计为"其他得分"。

分值一律取动作上实际记录的 `score_change`，不按 4 / 7 / 10 反推：2026-10-13（提交 `b845c61`）之前服务端不校验胜法与分值是否匹配，存量对局里可能出现分值不标准的胜局。

胜法归一为 `normal / small_gold / big_gold`，存量数据里的 `golden_break`、`nine_on_break` 分别归入小金、大金；无法识别的胜法计为"其他得分"，不丢分。

备选：继续以局记录为主、另查犯规数补上。否决——局记录没有犯规的顺序信息，拼不出流水，也仍会漏掉尾部犯规的归属。

### 2. 用对账决定是否可信

遍历结果的双方总分必须等于 `matches` 上的最终比分。不相等时得分构成标记为不可用，只返回总分，客户端退回到只展示比分。沿用复盘"宁缺勿错"的做法。

### 3. 契约：绝对位置（选手1 / 选手2），一个类型两处复用

`.api` 新增（名称在实现时可微调）：

- `ChasingScoreSide`：`score`、`normal_wins`、`small_golds`、`big_golds`、`foul_count`、`foul_points_given`（本方犯规送给对手的分）、`other_points`。
- `ChasingScoreEvent`：`seq`、`kind`（`normal / small_gold / big_gold / foul / other`）、`scorer`（得分方 1/2）、`points`、`player1_score`、`player2_score`（记分后的累计）、`created_at`。
- `ChasingScoreBreakdown`：`available`、`player1`、`player2`、`events`、`events_truncated`。

`MatchDetailData` 与 `PublicMatchDetailData` 各加一个可选的 `score_breakdown`。用绝对位置而不是"我 / 对手"，这样公开详情可以照常缓存，客户端沿用 `utils/match-detail.js` 现有的视角交换逻辑。

备选：把统计塞进现有的 `summary_stats` 文案条目。否决——条目是单列"标签 + 值"，表达不了双方对照，也没法承载流水。

得分构成与明细对公开对局的观战者同样开放（已确认），可见范围与现有"局记录"一致。

### 4. 有界

- 明细流水最多返回最近 200 条，超出时 `events_truncated=true`；统计数字仍覆盖全部动作。
- 沿用复盘的动作上限与计数口径（该场动作总数超过 5000 条，含已撤销）：超过时不计算得分构成，标记为不可用。
- 参与者详情：已经加载有效动作，不新增查询。
- 公开详情：目前只在斯诺克时读取动作。已完成的九球追分对局复用核心摘要缓存里的动作，不新增查询；进行中的九球追分对局新增两次按对局 id 的查询（动作计数 + 有效动作列表），超过上限时不读列表。

### 5. 结算总结条目

`buildNineBallSummary` 的统计条目收敛为不与对照表重复的内容（胜率、双方合计得分、最高连续得分、记录时间）；亮点保留小金、大金、最高连续得分。普胜 / 小金 / 大金 / 犯规的双方数字由 `score_breakdown` 承载。原生 iOS 目前不面向用户，不为它在条目里保留重复的胜法摘要；iOS 完整版开发时直接接 `score_breakdown`。

### 6. 复盘改为整场口径

九球追分的复盘：

- `frames` 只返回一个代表整场的片段：整场得分走势（不超过 60 点，沿用现有降采样）、双方最大连续得分、胜方曾落后的最大分差、整场用时。不标决胜局。
- `summary` 新增可选的 `score_breakdown`（同上类型，不带流水），不再填 `my_frame_wins / opponent_frame_wins`。
- 响应新增可选的 `viewer_actor`（查看者是选手 1 还是选手 2）：得分构成是固定位置，复盘其余数据是"我 / 对手"视角，客户端靠它对齐。
- `frame_count` 与锁定状态的返回不变（仍是胜局记录数，不新增查询）；复盘页在九球追分时不展示这个数字。
- 响应里仍用 `frames` 数组承载这一个整场片段，是为了不改响应结构；它不代表"一局"，客户端按球种决定标题。
- 动作对不上或超长时，沿用 `frame_only / detail_truncated`，只返回总分。

备选：保留逐"局"切片，只改文案。否决——九球追分的一"局"通常只有零到几次犯规加一次胜局，逐局走势没有信息量，也正是用户指出的口径问题。

这与 `revamp-vip-benefits` 中 `member-benefits` 规格的九球追分条目（"每局得分走势"）不一致。该变更尚未归档，已确认在实现本变更时同步修改其 delta spec 的九球追分条目（任务 3.4）：把"每局得分走势"改为引用本 capability 的整场口径，只动九球追分这几行，不改其他球种与该变更的代码任务。两个变更归档顺序不限。

### 7. 进行中对局的实时更新

详情页在九球追分时，收到 `score_update` 或 `round_end` 后重新拉取详情来刷新得分构成（短时间内多条消息合并为一次请求），不在 WebSocket 消息里新增字段。记分页只需要总分，现有消息已足够。

备选：在 WS 快照里下发流水。否决——观战详情页的刷新频率低，为它扩 WS 协议不值得。

## Risks / Trade-offs

- [2026-10-13 之前的存量对局：含 `score` 动作、旧胜法代码、分值不标准的胜局，个别可能对账不过] → 归入"其他得分"或归一映射，分值取实际记录；对账不过则整体降级为只显示总分，这类对局在详情页会同时失去原来的"局记录"列表。动手实现前先只读抽样存量九球追分对局，确认对账通过率；通过率偏低时先回来调整降级方案（例如退回按局记录统计胜法次数）。
- [公开详情多一次动作读取] → 仅九球追分触发，按对局 id 索引、受 5000 条上限约束；补 query-count 测试。
- [详情页实时刷新增加请求：进行中的公开详情没有响应缓存，每个观战者每次记分都会重新请求] → 合并短时间内的消息并加随机延迟；只在九球追分且对局进行中触发。观战人数多时再考虑改为 WS 下发。
- [复盘响应结构对九球追分变化，已发布的小程序旧版本会把整场片段显示成"第 1 局"] → 复盘页仅会员可见、用量小；后端与小程序同批发布，旧版本展示不报错，只是标题不准。
- [原生 iOS 战报页的统计条目里不再有本人普胜 / 小金 / 大金次数（亮点里的小金、大金仍在）] → iOS 目前不面向用户，已确认可接受；iOS 完整版开发时接 `score_breakdown`。

## Migration Plan

无数据迁移。先发后端（字段均为新增可选），再发小程序与鸿蒙。回滚时客户端回到旧版本即可，后端新增字段无副作用；复盘口径的回滚需要后端一并回退。
