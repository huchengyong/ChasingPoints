## Context

依据 [PRD V1.3](../../../docs/prd/familiar-player-quick-start.md)、[低保真 W1.3](../../../docs/prd/familiar-player-quick-start-wireframes.md) 和[仅模拟数据的 HTML 预览](../../../docs/previews/quick-match-ui/README.md)。目前 `challenge` 仅支持好友、24 小时待回应与扫码后用 `challenge_id` 关联比赛；生产 `/api/match/start` 要求签名 `invite_token`。`StartMatchLogic` 已用双方用户行锁避免重复正式比赛，比赛结束结算集中在 `FinishMatchLogic.settleMatchWithTx`，但无裁判排位需双人确认，灵活赛制自动结束也会进入待确认。`GetUserBootstrap` / `app/store/activity.js` 已承接双主 Tab 的当前比赛。项目未上线，无旧邀约兼容要求。

## Goals / Non-Goals

**Goals:** 两人无需扫码和重选比赛信息各点一次进入；先进入者等待而不创建比赛；约球状态、比赛状态、通知和两个主 Tab 可跨设备恢复且并发结果唯一；约球比赛由任意参赛方合法地单方滑动结束并同步释放约球。

**Non-Goals:** 陌生人搜索、聊天、订台、到场核验、多场已接受排期、独立等待倒计时；改写比分/排位结算算法；用 HTML 预览脚本充当生产实现；扩大清理范围到无关数据。

## Decisions

1. **沿用 `challenges` 作为约球主记录，不增加第二套邀约系统。** 扩展并在迁移中调整其球种、比赛类型/公开范围、必要赛制、实际预约日期与小时、失效时刻、双方是否主动进入、终态原因、互邀归并指向及查询索引；在 `matches` 增加唯一且可空的 `challenge_id`，作为比赛来源与约球关联的**唯一权威字段**，按它反查历史中的 `match_id`（旧 `challenges.match_id` 不再写入，可在本轮重构移除）。账号隐私新增默认关闭的 `friends_only_challenges`。主记录状态按「待回应 → 已接受（带等待方）→ 已开局 → 已完成/对局取消」或「拒绝/取消/放弃/过期」流转；归并记录仅保存指向主记录的别名，任何旧通知 ID 先解别名再查权威状态。匹配成功以后以**被点击接受的邀请**为主记录，时间与其他开局字段均取它；并发相反方向接受以先提交的主记录为准。历史列表去重显示主记录，不让别名变成第二场约球。一条主记录最多关联一场比赛，关联后不能过期或被取消；比赛终态直接按 `matches.challenge_id` 更新对应主记录。现有 `/match/start` 携带 `challenge_id` + 扫码关联链路在这轮替换，未上线旧邀约不兼容；普通无约球扫码仍保持签名验证。App 选人页只展示好友和最近对手，但服务端允许好友或**任何曾有真实比赛记录的平台对手**（包括从久远历史详情再约）；用有索引的存在性查询校验，不以客户端候选列表或无界历史扫描作为授权依据。比另起一套表/重复历史更少分叉。

2. **服务端决定时间和状态，不依赖后台清理。** 发送端传「今天/明天/后天」相对选择、当时展示的实际预约日期、0–23 开始小时、1–24 结束小时；服务端按 Asia/Shanghai 的提交时刻校验相对选择与实际日期对应（跨午夜编辑不静默滚到另一日），拒绝无效或已经完全过去的区间，算出该**预约日期次日** 07:00 的绝对失效时刻（23–24 点不多延一天），绝对时刻存取/查询统一 UTC，避免 MySQL 会话时区改变边界。应答（含 Bootstrap）返回绝对日期、小时、`expires_at` 和服务端时间；App 用服务端时间基准而非手机的本地时区/修改后的时钟更新可见文案，前台恢复及时回源；读取按当前服务端时刻派生未开局约球的有效状态，查询用 `expires_at > now` 排除已失效记录，即使过期 worker 未运行也不占用资格、不允许接受/进入。GET 不更新表；现有过期 worker 仅异步落库/分发终态，覆盖已接受与待回应，带条件更新防止改写已开局记录。客户端仅负责用北京时间格式化今天/昨天、跨午夜与回前台刷新展示；涉及操作再由服务端校验。

3. **全部竞争写入走同一个事务边界。** 发起、接受（含关闭自己发出的另一条邀请）、互邀归并、进入、退出等待、取消、拒绝及放弃：锁相关用户行（包括换人接受时自己原邀请的接收方，按 ID 升序），再按 ID 顺序锁有关邀约行，事务内重新校验有效状态、同账号最多一条有效已发出待回应邀约及最多一条未结束已接受约球；只对有效未结束状态施加限制，收到的待回应邀请不算占用。更换对象先提示确认，服务端一次提交接受与关闭旧邀请；无效/竞争失败则事务全部回滚。只有同一人+球种+比赛类型匹配互邀，类型不同时保持双方待回应；重复点击返回已确定的主记录。`enter` 在事务中核实另一人是否仍等待、双方无正式比赛、约球未过期：若**无人等待且未到预约开始**，未携带本人本次确认的请求只返回「需提前进入确认」且不写等待；App 弹一次提示后显式确认再试，避免对方刚退出时用旧卡片悄悄让自己等待。第二个进入者复用正常建比赛逻辑的赛制/身份及信誉禁赛等开局约束（不能绕过原开局限制），创建带唯一 `challenge_id` 的 `matches` 行并关联约球；首个进入者只写本人等待位，不创建 match/round/action。比赛创建后的重试只恢复**该约球绑定的比赛**，不得根据同对手同球种的其他比赛误判成功。退出等待和取消/放弃与进入以事务先提交者为准。普通扫码创建另一场正式比赛时，在现有 `StartMatchLogic` 事务内仅清除本人旧约球等待位，约球继续有效；普通扫码仍必须使用签名凭证，携带 `challenge_id` 不能作为绕过两人进入的捷径。相比客户端写入互相补偿，服务端串行和单笔提交能避免假比赛与丢邀约。

4. **只给约球比赛改变结束授权，沿用已有结算入口。** 创建时由已保存的约球选项生成比赛，排位设置 `finish_confirmation_required=false`；`/api/match/finish` 继续检查真实参赛者、合法赛制结束点、revision 和 action 幂等。对 `matches.challenge_id` 非空的比赛，若有裁判，仅放宽**结束比赛**给两位参赛方，其他记分/撤销权限不变；旁观者及非参与者不能结束。HTTP 当前对局/详情、WebSocket 与记分权威快照均返回该来源标识和一致的 `can_finish`，App 才能区分滑动与普通结束流程。练习、排位、斯诺克/灵活赛制的自动完成均复用现有 `settleMatchWithTx`，在同一事务中按本场比赛精确更新约球为已完成；正式比赛取消、作废路径同理在事务内写正确终态；当前 `CancelMatchLogic` 是事务外读取再 `Save`，必须改为锁定比赛后重检状态/版本并提交，避免与结束结算竞争时用旧对象覆盖赛果；账号注销沿用现有关系清理规则并确保另一方无残留活动占用，不能只在赛果页同步。无约球比赛保留原双确认/裁判行为。比赛已终结后的旧结束请求、旧通知和跨时刻 worker 不得变更后来新约球。客户端只在滑块从左端达到终点并松手（触摸/鼠标/键盘）时提交一次结束；半途、取消、点击轨道复位，服务端仍以身份/规则校验为安全边界，不把滑动姿态当凭证。比重做结算或全局移除确认更小且不破坏即时扫码对局。

5. **现有聚合读和 API 门面承接双入口。** 在 `backend/chasing_points.api` 调整 `/api/challenge/send|accept|reject|pending`，补 `cancel|enter|leave|abandon|detail|history` 等必要路由；返回主记录 ID、权威状态、等待方、比赛 ID 与失败原因。`GET /api/user/bootstrap` 添加当前约球、服务端时间及待回应收到邀请数量，保持 `availability` / `partial_errors` 和纯读；列表分页及详情按参与者鉴权，查询有界、稳定排序。修改 `.api` 后**立即**运行 goctl，logic 落在对应 `logic/<group>`，不得提交生成的 `todo` 空壳。通知数据只传约球 ID 并定位详情；沿用 `DispatchNotification`、user WS 作为失效提示，写入提交后才广播，丢消息靠 bootstrap/详情回源。App 通过 `api/challenge.js`、`api/user.js` 和现有 `activity` Store 为两主 Tab 提供同一状态，WS/写操作精确标脏，身份及 authGeneration 隔离旧请求，加载失败不显示虚构空态。设置读/写返回明确两个隐私字段，更新采用字段存在性语义，不能切换好友开关时把隐藏战绩误清零。

6. **复用现有页面结构。** 「对局」首屏有活动卡、约球记录和收到邀请入口，原扫码开局仍在；「我的」仅使用现有 status-card，优先显示正式比赛，其次已接受/等待约球、自己发出的有效邀请，收到的待回应邀请只在没有更高优先级时露出且不堵发起。改造 `subPages/social/challenges.vue` 为收到/发出/记录页面，增加简短发起页和等待页并在 `pages.json` 注册；通知与比赛详情只导航到权威记录。新建表单借用对手候选与球种偏好，比赛类型及必须确定的赛制在发送时确定并可见；历史详情「再约一场」只预填对手、球种、可改类型，不沿用旧时间。比赛页对约球比赛使用滑动结束且无二次弹窗，包括菜单等现有替代结束入口也不能绕过滑块；改造 `opponentSelector.vue`、报表/H2H 中指向旧 PK 挑战的发送入口及 `pending_match_challenge` 扫码上下文，统一打开约球发起页；返回等待页不再次发 `enter`。所有页面遵循现有主题、跨端和无障碍习惯，不移植预览的桌面控制台或模拟时钟。

## Risks / Trade-offs

- **[对局终态来源分散]** → 把约球终态更新放到共享结算事务和实际取消事务，补齐自动结束、平局、练习、裁判及账号删除后的无残留占用测试，禁止页面/通知来补状态。
- **[锁顺序/竞争导致死锁或重复开局]** → 双方用户锁及邀请锁固定顺序，进入已关联比赛时不在持有邀请锁后锁比赛；按比赛关联 ID 幂等重放，测试互邀、取消/进入、普通扫码与结束竞争。
- **[部分接口失败及用户切号]** → Bootstrap 分区报告失败而非当作无约球；客户端回前台/重连回源并按认证代次丢弃旧响应。
- **[存量挑战/旧测试结构不兼容]** → 仅未上线开发/测试/本地环境迁移或清理本次约球相关数据并更新相关用例；上线前备份、迁移后走双账号回归，不删除无关比赛或用户数据。

## Migration Plan

先更新 `challenges`、`matches.challenge_id` 与用户设置字段的 goose 迁移、模型和有界索引；在开发/测试/本地环境仅清理受影响的旧挑战记录，再按新流程造数。修改 `.api` 后立刻 goctl 生成并补齐真实 logic；接入 App 后跑后端 `go test ./...`、App `node --test tests/*.test.mjs`、迁移校验和双账号/第三账号现场验收。发布时迁移先于客户端、同批部署新 API；若必须回滚客户端/服务，先停用新约球入口并恢复同批备份的相关数据/迁移版本，不让旧客户端写入新版约球表。无旧邀约数据转换。

## Open Questions

无；业务决策以 PRD V1.3 为准，实施前只需按现存各球种赛制校验补齐对应测试样例。
