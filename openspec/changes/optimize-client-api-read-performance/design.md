## Context

当前移动端没有通用 GET 缓存或请求 single-flight。TabBar 页面和多数子页面在 `onShow` 中无条件刷新，导致 App 前台恢复与首页重复读取当前对局，首页与“我的”重复读取角标和常玩球馆奖励，首页/排行榜、首页/赛讯也重复读取相同公共资源。认证请求还会先经过 `ActiveUserSessionMiddleware` 查询用户，业务 Logic 随后经常再次查询同一用户，因此请求数量本身就是数据库负担。

后端问题不止是重复读。`matches` 以发起方/对手两列保存参与关系，历史列表、H2H、对手统计和用户统计大量使用 `user_id = ? OR opponent_id = ?`，部分方法先加载用户全部历史再在 Go 中翻转视角、过滤或分页；好友、挑战、球馆、赛季榜单、裁判历史和公开对局还存在 N+1。规则、挑战、段位、赛事对阵、当前对局和奖励摘要等 GET 包含初始化、过期处理或补偿写入，使缓存边界不清晰。

用户已确认：

- 对局结果页的胜率和最高分必须是双方“当前最新数据”，不是比赛结束时快照。
- H2H 首屏采用单个 overview 接口返回资料、统计和首屏历史。
- 用户统计不再扫描全部历史，改为比赛结算时维护快照。
- 实施按低风险客户端治理、查询/读模型、聚合接口、Redis 缓存分批推进，且不得遗漏已发现问题。

当前 HEAD 新纳入的连续赛季生命周期对本设计有直接影响：在线当前赛季解析和荣誉墙会 `ListAll` 全部赛季；每分钟 Worker 在一次执行中多次 `ListAll`；换季事务加载整季有效比赛，再对每个用户球种执行两次段位日志查询；挑战归档先列出用户球种，再逐个汇总指标。虽然当前赛季表较小，这些路径会随赛季数、参与用户和比赛量线性增长。最新日志提交改为 JSON 文件日志，但实际配置仍为 `Stat: false`，`backend/tmp/logs/access.log` 仍为空，且 `chasing_points-api.yaml` 与未被主服务引用的 `chasingpoints-api.yaml` 保留了不同日志参数，因此尚不能用真实 QPS/P95 验证优先级。

实现必须遵守仓库约束：API 契约先改 `backend/chasing_points.api` 并立即运行 goctl；数据库只通过 migrations 变更；移动端页面只调用 `app/api`；使用现有 MySQL、Redis、go-zero、Gorm、Pinia 和 WebSocket，不引入收费、专有或非标准基础设施。

## Goals / Non-Goals

**Goals:**

- 把 App 前台恢复和页面首屏的重复 HTTP 请求降到按资源实际变化触发，而不是按每次 `onShow` 触发。
- 使用户统计、分球种统计、最高分、时长、H2H、对手列表、当前赛季记录和近期历史读取不再加载用户全部比赛历史。
- 为完成比赛建立可重建、幂等、面向参与者视角的统一读模型，避免各接口重复翻转双方视角。
- 通过页面聚合接口减少认证中间件、网络 RTT 和重复 SQL，同时保留分页、部分结果及 Redis 故障回源能力。
- 消除在线 N+1、Go 内存分页、精确经纬度全量距离计算和 GET 隐式写副作用。
- 让连续赛季在线读取和每分钟 Worker 使用确定性窗口、索引查询和增量快照，换季不再扫描整季比赛或执行用户级 N+1。
- 建立可量化的路由、SQL、缓存和移动端首屏性能验收基线。

**Non-Goals:**

- 不缓存或弱化登录、Token、支付、上传凭证、裁判二维码和进行中记分的一致性。
- 不把所有首页资源塞进一个巨型接口；位置授权和附近球馆继续独立，避免阻塞首页核心内容。
- 不引入 Elasticsearch、商业 APM、付费地理服务或新的分布式消息中间件。
- 不改变排位、信誉、会员、成就、赛季挑战和比分结算业务规则。
- 不把 Redis 作为用户统计真源；统计快照以 MySQL 为可重建真源，Redis 仅缓存共享或不可变读结果。
- 不在在线请求内执行历史读模型重建；历史回建只允许使用离线、可恢复、有界批处理。

## Decisions

### 1. 按依赖和风险分五阶段交付

实施顺序固定为：

```text
0. 可观测基线
1. 客户端重复请求治理
2. 索引、纯读边界、参与者读模型与统计快照
3. 页面聚合接口和客户端切换
4. Redis/持久静态缓存
5. 旧扫描路径清理与验收
```

第一阶段不依赖数据库迁移，可快速修复排行榜首次双请求、挑战 Tab 重复请求和 `onShow` 全量刷新。第二阶段先解决单次请求成本，避免聚合接口只把多个昂贵查询搬到同一个 Handler。聚合稳定后再增加 Redis，防止用缓存掩盖冷请求全量扫描。

**替代方案：** 先给所有 GET 加通用缓存。该方案会缓存带副作用或实时数据，并可能在账号切换时串数据，因此不采用。

### 2. 客户端使用领域资源 Store，不在 `request.js` 做 URL 级通用缓存

每个跨页面资源保存：

```text
ownerUserId / authGeneration
loaded / dirty / loadedAt
inFlight
value / lastRevision
```

同一资源的并发调用复用同一个 Promise。普通 `onShow` 只有在未加载、dirty、超过 TTL 或用户手动刷新时请求；已过期但仍有旧值时先展示旧值，再后台刷新。刷新失败保留旧值并暴露可重试状态。

资源所有权如下：

- `activity`：当前对局、未读通知数、好友申请数、最近未读换季通知。
- `userOverview`：用户统计、信誉、会员状态、常玩球馆奖励。
- 现有 `user`：用户资料。
- 现有 `rank`：四球种段位，取消 App 每次前台恢复的无条件 invalidate。
- 公共内容：赛讯、排行榜摘要、地区、规则、术语、会员套餐和附近球馆位置桶。

用户级数据第一期只保存在内存；需要持久化的静态公共数据使用 schema/app version、时间戳和内容版本。logout、账号合并、登录替换或 `authGeneration` 变化时同步清空所有用户级缓存和 in-flight。

**替代方案：** 建立一个高度抽象的缓存框架。当前资源数量有限，领域 Store 更容易表达不同失效事件，符合仓库“最少代码”原则。

### 3. App 前台恢复只执行一次 Bootstrap，实时变化由独立用户事件驱动

新增 `GET /api/user/bootstrap`，核心返回：

- 已由认证中间件校验的用户资料；
- 当前对局快照；
- 未读通知数与待处理好友申请数；
- 最近一条未读换季通知；
- 用户竞技数据 revision。

认证中间件把已校验用户放入 Context，Bootstrap 和后续 Logic 复用，不再次查同一用户。App 登录成功、冷启动和从后台恢复时最多调用一次 Bootstrap；首页、观赛和“我的”从 Store 读取当前对局与角标。

新增与通知偏好无关的 `user_data_updated` WebSocket 消息，携带 `scopes`、`competitive_revision` 和可选 `match_id/game_type`。比赛结算后分别向双方发送。通知 WebSocket 携带最新未读数或精确计数变化，避免收到 category 后再次同时请求两个 count。客户端可能在后台错过消息，因此前台 Bootstrap 的 revision 负责最终校准。

进行中比赛仍以 match WebSocket 为权威，HTTP 只承担首次快照与重连兜底。

### 4. 聚合接口只合并同页面、同权限、相近失效边界的数据

新增：

- `GET /api/user/overview`：统计、信誉、会员状态、常玩球馆奖励。
- `GET /api/stats/overview`：分球种摘要、近期趋势、段位趋势、最高分、时长和对手强度。
- `GET /api/match/h2h/overview`：对手资料、H2H 聚合统计、首屏历史、total。
- `GET /api/opponent/candidates`：批量查询后的好友与近期对手。
- `GET /api/season/overview`：当前赛季、指定球种本人记录、排行榜第一页。
- `GET /api/public/rank/leaderboard-summary`：前三名和当前用户排名。
- 通知列表响应增加 `unread_count`。

后续分页继续使用细粒度接口。旧接口在迁移期保留并切换到同一读模型，避免两套计算口径。

Bootstrap、用户概览、统计概览和赛季概览中的独立子查询可以使用 `errgroup` 并行，但并发数必须有界且不共享事务。认证失败或主资源失败时整体失败；非主资源失败时返回 `availability`/`partial_errors`，客户端保留其余可用区块。附近球馆保持独立，因为定位授权、地理计算和公共首页内容不共享失效边界。

### 5. 建立统一的比赛参与者投影，解决双列参与关系造成的重复扫描

新增可重建表 `match_participant_results`，一场已完成比赛为每名真实参与用户写一行，至少保存：

- `match_id + user_id` 唯一键；
- 对手用户 ID 或规范化访客身份；
- 球种、模式、结果、双方视角比分；
- 完成时间、时长、比赛级最高分/单杆；
- 对手在结算时的段位分档；
- 用于排序和分页的稳定 match id。

核心索引覆盖：

```text
(user_id, match_mode, game_type, completed_at, match_id)
(user_id, opponent_user_id, game_type, completed_at, match_id)
(user_id, opponent_name_key, game_type, completed_at, match_id)
```

比赛原表仍是写模型和事实真源；参与者表只是读投影。比赛成功结算的同一事务中，以 `match_id + user_id` 幂等 upsert 两个视角行。近期趋势、对局历史、H2H 历史和近期对手直接按参与者索引 `LIMIT/OFFSET` 或游标分页，不再使用 `OR` 加全量内存翻转。

对手强度按“比赛结算时的对手段位”归档，避免对手后来升降段导致历史分析反复变化，也使该指标可以增量维护。

### 6. 比赛结算事务增量维护可重建统计快照

新增或扩展以下读模型：

- `user_competitive_stats`：每用户总体行和每球种行，保存总场次、胜负、当前/最大连胜、比赛最高分、单杆最高分、时长 count/sum/min/max、最后比赛及 revision。
- `user_opponent_stats`：按用户、对手身份和球种维护场次、胜负、最后交手时间，供对手列表和 H2H 聚合使用。
- 对手强度桶快照：按用户、球种和结算时段位档位维护场次与胜场。
- 现有 `season_records`：当前赛季内随比赛结算更新 start/end/peak score、场次和胜场，结束时再发布 final rank。

结算只查询当前 `match_id` 的局/动作来计算该场最高分，不查询用户历史。唯一投影键决定该场是否已应用统计增量；重放 Finish、重试或多实例并发不得重复加总。快照更新、参与者投影和比赛最终状态在同一业务事务内提交，提交后再发送 revision/WS 失效事件。

总览统计从总体快照读取；分球种统计从四行快照读取；平均时长由 sum/count 计算；最高分直接读取快照；H2H 统计读取 `user_opponent_stats`；近期趋势和历史只读取有界参与者行。段位趋势继续读取已有按用户/球种/时间索引的 rank change log。

**替代方案：** 每个统计接口分别增加 Redis。它不能解决冷启动或缓存失效后的历史扫描，也使失效键数量增加，因此采用数据库增量读模型。

### 7. 对局结果拆分为不可变核心与当前用户指标

对局结果服务拆成：

```text
完成对局核心摘要（比分、局、动作摘要、段位变化、成就、完成归因）
                         +
双方当前统计快照（当前胜率、当前最高分、revision）
                         =
结果页/分享页响应
```

核心摘要只依赖该 `match_id` 及其局/动作/奖励数据，进入 ready 后可长期 Redis 缓存；pending 奖励状态不缓存。双方胜率和最高分每次从最新 `user_competitive_stats` 读取，因此即使之后又完成新比赛，旧比赛结果页也展示当前最新值。组合响应不做长时间固定缓存，或将双方 snapshot revision 纳入键。

`getMatchDetail`、`getPublicMatchDetail`、`getMatchShareData` 和结果页复用同一核心摘要 builder，不再分别计算用户全部历史。分享页面优先复用结果页已取得的数据，深链进入时再调用共享服务。

### 8. 所有在线读查询必须有界、可索引且无 N+1

具体治理：

- 对局列表、H2H、对手列表、近期趋势切到参与者投影，数据库分页而不是 Go 切片。
- 好友列表、好友申请和挑战使用 JOIN 或一次 `IN` 批量读取用户/段位；好友申请角标使用独立 `COUNT` 或 Bootstrap，不再用 `page_size=1` 加载完整申请。
- 挑战状态在查询条件中按 `expires_at` 解释，状态收敛由按索引分批 Worker 处理，不在 GET 中执行全局 UPDATE。
- 球馆列表在单个查询中聚合签到数；附近球馆先按经纬度边界框或已有可索引地理字段缩小候选，再对有限候选计算 Haversine，缓存键使用位置桶。
- 赛季榜单、裁判历史和公开比赛通过 JOIN/子查询一次取得用户和局数；赛季榜单增加覆盖排序的组合索引。
- 规则默认数据由 migration 或启动期一次初始化；段位行由用户创建/显式修复初始化；赛事 bracket 由赛事创建/显式生成命令产生；奖励补偿由可重试 Worker 处理。
- 当前对局 GET 不再主动写过期结束请求；读取可返回基于时间的有效状态，由按索引 Worker 收敛持久状态。
- 认证中间件查询到的用户放入 Context，Logic 优先复用。

每个热接口增加 query-count 测试和代表性 `EXPLAIN` 验证。在线路径不得使用无 `LIMIT` 的历史列表、先 `Find` 后内存分页、每条结果再查关联数据、没有候选范围的精确距离计算，或通过 `COALESCE`/函数包裹关键时间列导致索引失效。需要统一完成时间时，增加并维护可索引的 `completed_at` 字段并批量回填，不依赖 `COALESCE(end_time, match_time)` 作为长期热查询条件。

### 9. Redis 只缓存共享、静态或不可变数据，并按领域版本失效

缓存策略：

| 数据 | 客户端 | 服务端 | 失效 |
|---|---|---|---|
| 赛讯列表/详情 | 3～5 分钟 SWR | 保留现有 5/3 分钟版本缓存 | WST/admin 写入 bump version |
| 公共排行榜共享部分 | 15～30 秒 | Redis，按球种/分页/version | 排位结算、昵称/头像变化 |
| 规则、术语、地区、段位配置、会员套餐 | 持久缓存 | 进程内或 Redis | 配置/schema/app version |
| 球馆列表/附近 | 3～10 分钟，按位置桶 | Redis | 审核、资料、签到版本或 TTL |
| 当前/历史赛季公共信息 | 至边界或短 TTL | Redis/进程内 | 生命周期/结算版本 |
| 已完成对局核心摘要 | 页面复用 | 长 TTL Redis | 核心 ready/version 变化 |
| 用户统计/H2H/会员/信誉 | 内存 Store + revision/TTL | 首期直接读 MySQL 快照 | 业务事件 |

Redis 读取失败、反序列化失败或写入失败必须回源，不影响核心响应。热点共享 key 可使用进程内 single-flight 防止击穿，但不构建通用缓存框架。

以下不得普通响应缓存：认证/短信/Token、支付状态、上传凭证、裁判二维码/加入、进行中对局快照及记分写操作、用户搜索、pending reward、包含隐式写入的旧 GET。公开进行中比赛先优化 SQL；只有指标证明需要时才允许 1～2 秒微缓存。

### 10. 连续赛季采用确定性窗口快路径与增量记录

在线解析不再读取全部赛季。根据 policy 和当前业务时间先计算期望窗口，再使用唯一 `start_date` 或窗口索引查询当前记录，并对有限的相邻/重叠候选做一致性校验。缺失或冲突返回 `unavailable`；完整历史冲突审计只由修复命令执行。

每分钟 Worker 快路径只查询：期望当前/下一窗口、按 `end_date/status/settlement status` 索引找到的到期未结算赛季。正常稳定状态不得重复多次 `ListAll`。长时间停机追赶时按开始日期分页处理未结算窗口。

当前赛季 `season_records` 在每场排位结算时增量更新，因此赛季页在赛季进行中即可读取本人数据和榜单。换季不再扫描 `matches` 或逐用户查询 rank logs；它基于已维护的 season records 计算最终名次。挑战归档使用一次按赛季时间范围和用户/球种/指标分组的聚合查询及专用索引，替代先列 pair 再逐 pair SUM。最终名次、称号、挑战快照和通知采用可恢复的幂等阶段；只有所有必要阶段完成后才把 settlement 标记 completed 并发布已结束赛季，避免长事务包住整季原始数据扫描。

赛季 repair/rebuild 允许检查历史，但必须按窗口和主键游标分批，不得一次加载全部赛季、比赛、事件或日志。

### 11. 异步和并行只用于可重试、可界定的工作

- 读模型历史回建按 `match.id > cursor ORDER BY id LIMIT batch_size` 处理，保存检查点，支持 dry-run、暂停、恢复和重复执行。
- 挑战过期、奖励补偿、旧完成时间回填和赛季追赶按索引分批，不持有跨批次事务。
- WebSocket/Push 和 Redis 失效在数据库提交后执行；失败不会回滚比赛，客户端通过 revision/前台 Bootstrap 最终收敛。
- 聚合接口只并行无依赖查询，设置固定上限；不为每个列表元素启动 goroutine，也不以并行掩盖 N+1。
- 所有投影写入使用唯一键/last applied match，确保至少一次执行不会重复计数。

### 12. 使用实际生效配置和标准指标验收

`backend/etc/chasing_points-api.yaml` 作为唯一运行配置真源。确认仓库和部署脚本均未使用 `backend/etc/chasingpoints-api.yaml` 后移除或明确废弃后者，避免 3/7 天保留期和 Encoding 配置漂移。保留 JSON 文件日志，并启用 go-zero 标准统计或等价的低开销请求完成日志。

每个请求至少记录：method、规范化 route、status、duration、response bytes、request id；慢查询记录 SQL 模板/耗时而不记录 Token、手机号等敏感值。生产或压测环境采集：

- route QPS、P50/P95/P99、错误率和响应大小；
- 每请求 SQL 次数、SQL 总耗时和慢查询；
- Redis hit/miss/error、回源次数；
- App 冷启动、前台恢复及各核心页面首屏请求数。

测试为已知热点设置查询次数上限，并验证数据量扩大后查询次数不随列表长度线性增长。阶段上线前后用同一数据集对比，而不是仅以“代码有缓存”作为完成标准。

## Risks / Trade-offs

- **[投影与快照可能因历史数据或重试不一致]** → 所有投影可从 match 真源重建，使用唯一键和 last applied match 幂等；上线前双读抽样比对，提供审计命令。
- **[比赛结算事务增加写入量]** → 每场只写固定数量的参与者、统计、对手和赛季行；使用复合唯一键和原子增量，避免在线历史扫描，写放大是有界的。
- **[并发完成或重复 Finish 导致重复统计]** → 以 `match_id + user_id` 投影插入是否首次成功作为增量门闩，并沿用比赛完成幂等机制。
- **[客户端缓存显示短暂旧值]** → 业务事件立即 dirty，WebSocket 推送 revision，App 前台 Bootstrap 兜底，手动下拉强制刷新；实时比赛不走普通缓存。
- **[聚合接口扩大单次失败范围]** → 区分主资源与可选区块，返回 availability/partial errors；后续分页及旧细粒度接口保留过渡。
- **[排行榜或球馆缓存失效遗漏]** → 保留短 TTL 兜底，写链路统一 bump 领域版本，Redis 故障直接回源。
- **[历史回建耗时]** → 按主键游标小批量处理并限速，可暂停恢复；不在 migration DDL 或在线请求中同步回放全部历史。
- **[赛季 staged settlement 与原单事务语义不同]** → 所有中间产物带 settlement/version 且不可对外发布，最后使用小事务原子切换 completed/status；重复运行从未完成阶段继续。
- **[新增组合索引增加写成本和磁盘]** → 只保留被明确查询使用并经 `EXPLAIN` 验证的索引，移除重复/无效索引。
- **[日志和 SQL 指标产生额外开销]** → 使用结构化低开销字段、慢查询阈值和必要采样；压测验证观测开销。

## Migration Plan

1. 统一日志配置并采集现状基线；记录核心页面请求数和热点接口 SQL 次数/P95。
2. 完成纯客户端低风险调整：single-flight、loaded/dirty/TTL、排行榜与挑战修复、用户资料复用，保持现有 API。
3. 修改 API 契约增加聚合响应、revision 和必要字段，立即运行 goctl；先部署兼容但尚未切换客户端的后端。
4. 通过 migrations 新增 `completed_at`、参与者投影、用户统计/对手统计快照、必要唯一键与组合索引；DDL 不执行历史全量更新。
5. 在比赛结算中双写新读模型；新增比赛开始产生正确投影和快照。部署可恢复 rebuild 命令，按 match id 批量回建历史并记录 checkpoint。
6. 使用审计命令抽样比较旧计算与新快照，包括双方视角、访客对手、四球种、连胜、最高分、H2H 和赛季边界；差异归零后切换细粒度接口读取新模型。
7. 优化好友、挑战、球馆、赛季、裁判和公开对局批量查询，移除 GET 写副作用；验证 query-count 和 EXPLAIN。
8. 发布 Bootstrap、用户/统计/H2H/赛季 overview、对手候选和榜单摘要，并切换 App 页面；保留旧接口一个兼容周期。
9. 增加公共/静态/已完成对局 Redis 缓存和客户端持久缓存，观察命中率及回源行为。
10. 改造连续赛季 Worker 与 settlement 使用有界窗口和增量 records，执行赛季 repair dry-run 后上线。
11. 达到验收阈值后删除旧全量扫描 helper、重复 Logic 和未使用配置文件；保留读模型重建工具作为灾备。

回滚时客户端可临时退回旧细粒度接口；新表、索引和双写保留，不删除已生成快照。Redis 可直接禁用并回源。若读模型校验失败，停止切换读取并重新从 checkpoint 回建；不得回滚已完成比赛或用户资产。

## Open Questions

- 各路由最终 P95/P99、首屏请求数和 Redis 命中率阈值需要先用阶段 0 基线确定；设计先要求查询次数有界且不随结果条数线性增长。
- 历史数据量与生产允许的回建速率尚未知，batch size 和限速参数需在 dry-run 后确定，但回建协议和幂等边界不变。
