## Context

原生工程最低支持 iOS 17.0。`APIClient` 已支持 URLSession、蛇形字段转换、Bearer token 和基础错误解析；`SessionStore` 已实现 Keychain、启动恢复、401 刷新、共享刷新任务及 `authGeneration`；`LoginView` 已有手机号/六位验证码校验、协议确认、发送倒计时和提交状态。

目前缺少原生测试目标和完整的真实账号链路验收。源码核对还发现，验证码错误可能由后端返回 HTTP 400 纯文本，原生端只解析 JSON 错误时会退化成“请求失败”。现有能力应先建立验证，再做必要修复。

当前接口事实如下；实施时需核对实际部署版本：

| 接口 | 请求 | 响应与边界 |
| --- | --- | --- |
| `POST /api/auth/send-sms` | `phone`、`scene: login` | 顶层 `success`、`message`；发送失败或频控可能为 HTTP 200 + `success: false` |
| `POST /api/auth/login` | `phone`、`sms_code` | 顶层 `success`、`access_token`、`refresh_token`、`expires_in`、`user_info`；验证码错误/过期可能为 HTTP 400 纯文本；新手机号会自动注册 |
| `POST /api/auth/refresh-token` | `refresh_token` | 顶层新令牌对及 `expires_in`；失效可为 HTTP 200 + `success: false` + `reason: SESSION_INVALID` |
| `GET /api/user/info` | access token Bearer 认证 | 顶层 `success`、`user_info`；已删除/停用用户返回 HTTP 401 + `SESSION_INVALID`；普通 JWT 401 允许尝试刷新 |

四个接口的成功响应不需要 `data` 包装。`user_info` 包含 `id`、`phone`、`nickname`、`avatar`、`status`、`created_at`；登录响应中的手机号已经脱敏。当前短信为六位、有效期五分钟、发送间隔六十秒，未发现固定测试验证码入口。当前配置 access token 七天、refresh token 三十天；这不是测试时可以直接等待的周期。

## Goals / Non-Goals

**Goals:**

- 让现有原生短信登录到本机退出链路可用、可重复验证，故障反馈准确。
- 保留仍可能有效的凭据，只在明确失效时清理；保证并发和迟到响应不跨会话生效。
- 提供分层验证结果和复现步骤，明确真实后端验收是否完成。

**Non-Goals:**

- 业务页面迁移、第三方登录、绑定/合并、注销、WebSocket、推送和业务缓存。
- 新建网络框架、主动定时刷新机制或完整认证路由框架。
- 修改数据库结构、统一重写后端错误格式或增加服务端全设备令牌撤销。
- 在本次提案阶段发送短信、测试真实账号或修改应用代码。

## Decisions

### 1. 复用现有四个接口，在原生请求层补足错误兼容

保留当前 URLSession 方案。按 HTTP 状态、业务成功标记和 `reason` 判断结果；HTTP 200 的 `success: false` 必须抛出业务错误，不能进入登录成功或发送成功状态。

错误展示优先采用有效 JSON 的 `message/msg`；对已核对的验证码错误、过期等用户可读纯文本保留具体反馈。对 HTML、堆栈、空体和未知服务内部错误使用适合其类别的通用中文提示，避免将整个响应体直接显示给用户。保留状态码与机器原因供会话层判断。

曾考虑统一修改后端错误响应，但这会扩大到 UniApp、管理端等调用者。本阶段按现有契约兼容，确有服务端缺陷再记录最小修复；若必须变更 `.api`，修改后立即执行仓库规定的 goctl 生成流程并核对受影响调用方。

### 2. 继续采用收到普通 401 后刷新一次的会话模型

配套的 `stale-auth-session-recovery` delta 将原有“普通 401 刷新失败即清理”限定为 UniApp 的既有行为，并明确原生 iOS 的清理条件为认证明确失效。本节和 `native-ios-auth-integration` 的刷新故障策略适用于原生 iOS；本变更的代码实施范围仍为原生端。

当前不增加 `expires_in` 驱动的定时器。单个原请求最多重放一次，同一会话的并发 401 共享刷新；较晚到达的旧 token 401 在凭据已更新时使用当前凭据，避免重复刷新。测试覆盖重叠与错峰返回，而不依赖固定延时制造时序。

| 结果 | 原生行为 |
| --- | --- |
| 普通 401 | 尝试共享刷新，成功后重放原请求一次 |
| 401 + `SESSION_INVALID` | 不刷新；清理当前会话，提示重新登录并引导登录页 |
| 刷新明确失效，含 HTTP 200 + `success: false` + `SESSION_INVALID` | 清理当前会话，停止重试 |
| 重放仍返回 401 | 清理当前会话，不再次刷新 |
| 断网、超时、5xx 或不能证明会话失效的解析错误 | 保留凭据，结束当前加载，提供准确错误和重试方式 |

并发清理规则仅适用于按上述条件已确认失效的原生会话。针对“多个原请求 401 → 共享 refresh 返回 503”的回归，须断言凭据保留，清理、重新登录提示及导航次数均为零；服务恢复后的新请求可以重新发起刷新并成功重放。

登录与刷新只有在响应含完整令牌、有效普通用户资料（登录时）且 Keychain 写入成功后，才发布成功状态。启动恢复用服务端用户信息确认身份，不能仅凭 Keychain 有值显示已登录。普通失败不能偷偷写入部分凭据。

### 3. 用认证代次约束所有异步结果，集中处理会话失效

沿用现有 `authGeneration` 和共享刷新任务，在登录、恢复、刷新、重放及失败清理时检查结果是否仍属于当前会话。退出/登录替换淘汰旧任务，迟到的成功与失效响应都不能写 Keychain、修改用户或触发新会话的登录导航。

明确失效的清理、提示与登录导航由统一入口处理，同一代次最多一次。复用当前“我的”登录路径，避免同时弹出多个页面或重复提示；主动退出回到未登录状态，不展示被动失效提示。初次启动没有凭据时保持访客状态。

测试只需为现有 `APIClient` 的 URLSession 注入和 Keychain 访问补充必要接缝；不为单一链路引入通用状态机框架。测试使用独立 Keychain service，并在结束时清理自身数据，不能删除开发者日常会话。

### 4. 将真实链路与可控异常测试分开验收

| 层级 | 核心验证 | 证据 |
| --- | --- | --- |
| 构建 | Debug/Release 编译、最低部署目标仍为 17.0、环境配置匹配 | 实际命令、Xcode/SDK 版本与结果 |
| 原生自动化 | 真实响应形态、错误分类、持久化边界、并发刷新、旧请求隔离 | 可复现测试命令、断言及请求计数 |
| 真实后端人工联调 | 实际收短信、登录、“我的”资料、杀进程重启恢复、真实刷新、退出后重启 | 运行环境、步骤、预期/实际、通过/失败/阻塞及脱敏证据 |

通过 URLProtocol 等本地测试夹具控制响应、并发和延迟，禁止测试使用生产数据或发送真实短信。Keychain 测试覆盖实际写入/读取/删除，并通过最小故障注入验证保存失败；UI 验证覆盖发送/登录按钮状态、协议确认、恢复重试和失效登录引导。

真实刷新使用隔离开发后端的短 access token 有效期和长于它的 refresh token 有效期：实际登录取得服务端签发的令牌，等待 access token 失效后从原生端发起请求，再验证刷新、重放和下一次重启恢复。当前 Debug 地址写在 `AppConfiguration` 中，需通过临时本地构建配置接入隔离实例，并使用独立测试 Keychain service；在验收记录中写明接入与回切步骤，不增加产品内环境切换入口。签名密钥仅在后端使用，测试配置不进入生产；不通过改写客户端 JWT 或生产绕过开关伪造成功。如果没有可用的隔离环境，真实刷新项记录为阻塞，可控测试单列通过，整条链路不能标为已完成。

人工联调前先确认模拟器/真机可以真实点击四个 Tab、进入登录页并输入。此前某个 Xcode Device Hub 与 iOS 17.5 runtime 组合曾出现鼠标触摸事件丢弃，XCTest 通过不能证明人工输入正常；需记录所用 runtime 和输入检查结果，不将其解释为所有 iOS 17 不受支持。最低部署目标与验收运行版本分别记录。

### 5. 维持环境隔离和本机退出语义

Debug 当前为 `https://dev-api.kekemate.cn` + `ChasingPoints.Session.development`；Release 为 `https://api.zhuifen.cn` + `ChasingPoints.Session.production`。验证配置及存储命名空间隔离，真实短信/失效实验仅在指定开发环境执行。客户端不需要短信供应商密钥或 JWT 签名密钥。

退出的范围是清空本机用户状态与本环境 Keychain 凭据，不承诺撤销其他设备会话或尚未过期的服务端令牌。验收使用杀进程/重启，不能用卸载重装代替 Keychain 清理验证。

## Risks / Trade-offs

- 开发部署版本可能与仓库契约不同 → 记录后端版本并核对实际响应，先定位差异再修复。
- 短信依赖数据库、Redis 和供应商，且新手机号登录会注册用户 → 在实际发送前确认可用的专用测试号与环境；验证码由测试人员在 App 输入。
- 默认令牌有效期过长，共享环境改 TTL 会影响其他人 → 使用隔离开发实例与临时配置，测试后恢复；不可用时明确阻塞。
- 模拟响应覆盖边界但无法证明短信、TLS 和部署链路正常 → 三层结果分别记录，真实必验项未通过不能宣布闭环完成。
- 错误体可能包含内部信息 → 只显示已确认的用户可读信息，报告不记录原始 token、验证码、密钥或完整手机号。

## Migration Plan

1. 固化四个接口的测试夹具和基线，建立原生测试入口及隔离存储。
2. 修复验证暴露的请求层、会话层和登录反馈缺口，保持 iOS 17.0 与既有 Keychain service/key 格式。
3. 运行自动化和构建检查，再执行指定开发环境的真实联调，填写 `docs/testing/native-ios-auth-integration.md`。
4. 恢复临时后端 TTL、原生本地地址与 Keychain service 配置，清理测试自身的 Keychain 与夹具数据；保留脱敏结果。

没有数据库迁移或全量凭据迁移。若修复需要回退，可独立回退对应 iOS 代码与工程配置；不依赖清空所有用户会话来回退。
