## Context

本设计基于当前后端代码及 proposal.md。`cmd/wst_sync/main.go` 已支持 `--year`、`--season`、`--from/--to`，并调用与自动任务共用的 `Service.Sync`。自动任务默认回看 30 天、前看 7 天；历史补采无需改动其时间窗口。

现有链路先选择赛季和赛事，再分页扫描对阵、准备记录、镜像图片，最后在事务内写入球员、赛事、对阵及赛讯。记录按来源 ID 查找并更新，成功后更新赛讯缓存版本。当前具体限制：

- `FetchTournamentsBySeason` 固定读取第 1 页、200 条，未遍历后续页。
- 对阵从第 1 页扫描到空页，没有识别服务端反复返回同一页的情况。
- JSON 请求已有最多 3 次的部分网络错误重试，但没有 HTTP 429/5xx 的退避处理。
- `deleteMissingOfficialMatches` 会删除已选赛事中此次源站未返回的旧对阵，历史补采不适合据此推断官方删除。
- 摘要主要是总量与 prepared 数量，不能说明各年份覆盖、实际事务提交或待核对问题。
- `MatchAttributes` 的整数/布尔零值无法区分缺失字段与官方明确返回的 0/false；现有状态推导还会仅依据过去的开赛时间推断完赛。
- 来源 ID 查询默认排除软删除记录，而已有迁移的官方来源 ID 唯一索引仍约束这些行，直接重建可能失败。

## Goals / Non-Goals

**Goals:** 一条命令补采官方可返回的 2023 年以来数据；可预览、可幂等重跑；发现分页和数据覆盖问题；失败时不留下半套事实记录；历史补采保留已存对阵。

**Non-Goals:** 不增加后台按钮、REST API、任务平台、自动历史扫描、持久化断点或新数据源；不承诺官方历史百分之百完整；不改移动端筛选和列表性能。本轮只提供提案，真实导入属于后续实施与运行。

## Decisions

### 1. 在已有命令增加显式补采模式

新增 `--backfill`，默认开始日期为 `2023-01-01`，结束日期为命令启动时的 UTC 当天。此模式下允许单独覆盖 `--from` 或 `--to`，未提供的端点沿用默认值；日期无效或结束早于开始立即报错。与 `--year`、`--season` 互斥，未启用该模式时保持原参数规则。

复用范围筛选：赛事起止日期与闭区间相交即纳入，资格赛和发布默认开启，沿用 `--include-qualifiers=false`、`--publish=false`、`--dry-run`。补采语义由一个明确的参数传至现有 service；不新增复制采集逻辑的命令或抽象框架。

WST 补采固定为斯诺克（`game_type=1`），其他球种值在请求前拒绝；原模式兼容性另行保持。命中已有官方赛讯时发布参数同样生效：`false` 会下架已有赛讯，`true` 会发布命中记录；dry-run 列出拟发布/下架数量，操作说明不得称作“仅控制新增赛讯”。

拟定使用方式（需实施后可用）：

```bash
go run ./cmd/wst_sync --backfill --dry-run
go run ./cmd/wst_sync --backfill
go run ./cmd/wst_sync --backfill --from 2023-01-01 --to 2023-12-31
```

### 2. 复用客户端，完成分页并限制异常循环

赛事列表遍历全部页，按来源 ID 去重；对阵继续全局分页一次，再按选中赛事 ID 筛选，不为每个年份重复全量扫描。先核实官方分页元数据；有可信的下一页/总量信息时校验其一致性，否则请求到空页结束，不把短页自行当作结束。

先检查列表响应包含协议要求的 `data` 数组；HTTP 200 下的错误对象、缺少 `data` 或非契约允许的 null 不能解码为空页。赛季目录同样检查分页/完整返回契约；某个赛季名称无法解析时纳入候选并依靠赛事日期过滤，避免只有全部名称解析失败才回退而漏掉部分赛季。记录这些回退项供核对。

无进展判断使用每一原始页面的所有有效来源 ID，必须在按目标赛事过滤之前进行；全页都是其他赛事的对阵仍是正常进展。完全相同的重复记录可去重；选中记录同 ID 的赛事归属或关键事实相互矛盾时停止，不采用任意先到/后到覆盖。未选中赛事的对阵不参与本次业务字段校验。没有官方快照或稳定排序契约时，去重和计数仍不能证明没有跳页，报告须说明运行期间源站可能变化。

对两种分页都识别非空但没有新增 ID 的页面，并设置固定的页数保护上限；触发保护属于失败，不能当作完整结束。上限在实测页数后确定并记录，日志注明当前赛季/页码以便调整。检查取消信号，使中断能结束请求与扫描。

CLI 通过标准库 `signal.NotifyContext` 接收中断，传递至 HTTP、退避、预检和 `DB.WithContext(ctx)` 事务。只给请求函数传 Context 而入口仍用 `context.Background()` 不算完成取消支持。

在现有 JSON 请求重试中覆盖短暂网络错误、429 和 5xx，沿用最多 3 次尝试，使用可取消的有界退避；429 尊重合法 `Retry-After`，超过等待预算则失败并提示稍后重跑。普通 4xx 和无效 JSON 不重试。只用 Go 标准库，不引入抓取框架。

### 3. 补采只新增或更新，不依据缺失删除历史

沿用现有来源 ID 匹配、事务、赛讯投影及缓存失效流程。显式补采模式跳过缺失对阵清理；自动同步维持原有清理语义。网络采集或必要字段校验失败时，在开始数据库写事务前退出；事务内任何事实写入失败均回滚。

未知赛事日期、无效来源 ID、对阵关联缺失需要区别处理：无法确认日期范围的赛事跳过并报告，必要 ID 或关联不合法导致事实写入无法成立时直接失败。官方无对阵的赛事仍可入库，但计入待核对清单，不生成虚构对阵或比分。

补采日期规则固定为：开始日期必须有效，结束日期缺失时以开始日期作为筛选端点；结束日期格式无效或早于开始日期则跳过并报告，不能用结束日期伪造开始年份。所有异常保留来源 ID 和原因。

在 dry-run 分支与镜像上传之前执行共用预检，允许通过 model 批量只读查询核对已存来源 ID、关联和发布状态。对命中的软删除球员、赛事、对阵或赛讯明确报错并列出 ID，整次补采不写入，不擅自恢复或创建替代行；不增加自动去重/恢复功能。已有重复活跃来源 ID 同样失败。现有唯一索引作为最后一道保障，预检不能替代事务错误处理。

对选中对阵保留比分、选手分配和状态等必要字段的“缺失/null”信息，按官方实际契约校验。明确的 0 分有效；必要事实缺失或状态不明的对阵跳过并列入待核对项，已有同 ID 对阵保持原样，不将缺失值写成 0，不仅根据开赛时间推断完赛。官方明确的待定选手、轮空/退赛遵守已核实的状态规则；不是所有空选手都属于错误。无需修改数据库列类型，以采集 DTO 的存在性信息和跳过策略解决。此语义仅作用于补采，避免改变日常对局状态推导。

批量比较已选赛事的已存对阵 ID 与本次返回/有效对阵 ID，列出保留的旧对阵和跳过的异常对阵，预览和导入使用同一口径。赛事状态及赛讯摘要应依据官方明确状态和合并后保留的有效对阵生成，不能因为本次响应退化而与数据库中的完赛记录矛盾。“范围外不变”指范围外赛事、对阵和赛讯；被选对阵引用的官方球员是共享资料，可以更新，人工来源记录始终不变。

继续遵循已有图片规格：镜像在事务外，dry-run 不检查或修改七牛对象、不写数据库。数据库回滚不能撤销先前已上传的图片，重跑依靠确定性对象键复用它们。

不建立断点表，失败后重跑相同范围即可；只有实测整段运行的内存或耗时不可接受时再考虑分批持久化。操作手册提供按年份缩小范围的现有参数方式。

### 4. 将执行状态与覆盖证据分别输出

扩展现有摘要而非新增报告服务。输出请求范围、模式、dry-run 标记、执行状态、扫描页数、去重后赛事/对阵/球员数、事务提交状态及耗时；按赛事开始年份归组展示赛事和对阵数量，跨年赛事只计入开始年份。每个请求年份都显示一行，包括零数据年份。

输出实际选中赛事的最早开始日期和最晚结束日期，以及缺失/无效日期、无对阵赛事的官方 ID 清单；最晚结束日期可以超出窗口，因为采用相交筛选。摘要区分扫描量、准备量和已提交数量，dry-run 或回滚时已提交数量为 0，不把 planned 数量称作新增数量。

无候选赛事或存在待核对项时标为 `needs_review`；成功写入且无已发现异常标为 `completed`，仍声明只覆盖此次接口返回的数据；请求/解析/分页/事务失败标为 `failed` 并非零退出。`needs_review` 不回滚有效数据，但返回独立的非零退出码供脚本识别。dry-run 使用同样的核对规则，并明确没有存储数据。运行日志可直接重定向保存，无需新建报告表或文件格式系统。

退出码约定仅作用于补采可执行文件：0 为 `completed`、2 为 `needs_review`、1 为 `failed`。自动任务不得把待核对状态作为新错误推进或阻止游标。调用 `go run` 时 Go 工具可能将程序非零码包装为退出码 1；需要区分 1/2 的脚本应先构建并直接执行二进制。命令退出前完成资源清理和摘要输出；已处理失败也输出已扫描的部分计数。

数据库提交后缓存失效失败属于 `needs_review`，保留真实已提交数量并提示缓存尚未刷新，不得标记为事务回滚。区分确认回滚与提交结果未知：COMMIT 期间连接断开等无法确认结果时输出 `commit_state=unknown`、提交量未知和 `failed`，要求按来源 ID 核对后幂等重跑；不能宣称为 0。事务开始前失败/已确认回滚才报告提交量为 0。

## Risks / Trade-offs

- [官方最早日期、历史比分与分页契约尚未实测] → 用只读预览记录证据，缺失年份必须保留为待核对项，不能据“2023 年应有数据”伪造完整性。
- [全局对阵扫描和内存准备较慢] → 每次补采仅扫描一遍全局对阵，记录页数、耗时和代表性内存占用；必要时按年份缩小存储范围，但说明这不会减少单次全局分页的请求量。
- [补采与多个自动任务并发写入同一赛事] → 首次导入采用维护窗口，暂停所有实例的 WST 自动任务并保证单个补采进程，导入后恢复；不在本变更新增分布式锁。
- [保留旧对阵可能保留官方已撤销记录] → 历史保留优先，异常由核对清单和人工处理；不增加自动历史删除能力。
- [软删除来源 ID 仍占用唯一索引] → 批量只读预检并明确失败，由数据负责人处理后重跑；运行环境需已应用现有迁移，不新增恢复语义。
- [导入成功不等于前台默认筛选会展示所有历史] → 以数据库关联核对和已有按日期查询作为验收，前台默认仍显示原时间范围。

## Migration Plan

1. 实施 CLI、分页、错误处理和核对摘要，完成本地定向测试；不需要数据库迁移。
2. 在选定运行环境执行从 2023 年起的 dry-run，保存日期覆盖、年份数量和异常清单；先核实官方实际可用范围。
3. 在有备份的目标环境维护窗口内单进程执行正式补采，核对四类记录的来源 ID、关联和历史比分，再重跑同范围验证幂等。
4. 恢复自动任务，验证近期更新及历史记录保留。补采不得写入 `wst_sync_job_states` 或扩大自动任务时间窗口。
5. 失败时重跑原范围；代码回退不删除已导入历史。若确需撤销已成功提交的数据，按运行前备份恢复，禁止依赖宽泛删除脚本。

自动任务恢复后的历史保留保证仅针对其查询窗口以外的记录；重叠窗口仍遵循原自动清理逻辑。应用配置暂停任务后须等待已运行的采集结束，且维护窗口内避免其他官方赛讯写入。MySQL 验收应包含现有生成列唯一索引与软删除冲突，SQLite 测试通过不能代替这一项。

## Open Questions

- 官方现有接口最早返回哪个赛季，2023 年赛事和对阵是否都仍可获取？由首次真实 dry-run 回答。
- 官方分页响应是否提供可信总数/下一页，是否存在服务器页大小上限或重复页行为？先取脱敏样本再固定终止校验。
- 整段 2023 年至今采集的实际体量是多少？以实测选择整段执行或现有日期范围分次运行，不提前增加调度和断点系统。
