## Why

持久化 JWT 可能仍在有效期内，但其 `user_id` 已因账号合并、用户停用或开发数据重置而不再对应有效用户；当前后端会以 HTTP 200 返回 `success: false`，客户端又把这类业务失败统一展示为网络异常，导致用户长期停留在伪登录状态并收到误导提示。需要统一失效会话语义，让账号身份、令牌和本地持久化状态重新保持一致。

## What Changes

- 将“JWT 有效但对应用户不存在或已停用”统一识别为登录会话失效，不再由各业务接口返回无消息的空失败响应。
- 在 REST 与 WebSocket 鉴权边界拒绝 refresh token，并在 WebSocket 升级前确认普通用户仍存在且启用；停用用户不得通过任一登录入口获得新会话。
- **BREAKING（仅错误语义）**：失效会话从 HTTP 200 + `success: false` 调整为 HTTP 401，使现有统一请求层能够执行退出与重新登录流程；有效用户的成功响应保持不变。
- 在移动端启动或恢复持久化登录态时验证服务端会话，不能仅凭本地 `token`、`userInfo` 或 `isLoggedIn` 判定已登录。
- 统一清理 access token、refresh token、Pinia 持久化用户状态及依赖用户身份的缓存，避免只清一部分后再次恢复伪登录状态。
- 保证手机号绑定发生账号合并后，客户端要么接收并应用目标用户的新令牌与资料，要么明确退出并进入重新登录流程，不得继续使用已删除用户的令牌；完成原子替换时不再提示用户重新登录。
- 区分登录失效、权限拒绝、服务异常和真实网络失败；荣誉墙等页面不得再把非网络错误统一提示为“请检查网络”。
- 增加后端、请求层、用户状态、账号合并和页面反馈回归测试，覆盖有效 JWT 指向缺失用户的真实故障场景。

## Capabilities

### New Capabilities
- `stale-auth-session-recovery`: 定义失效用户会话的服务端判定、HTTP 401 语义、客户端持久化状态校验与清理、账号合并后的会话替换，以及用户可理解的失败反馈。

### Modified Capabilities

无。当前主规格中没有已发布的认证会话能力。

## Impact

- 后端：JWT 认证后的 token 类型与用户有效性校验、登录入口、REST/WebSocket 认证错误响应、手机号绑定与账号合并响应，以及仍自行返回空 `success: false` 的当前用户接口。
- 移动端：`app/utils/request.js`、`app/store/user.js`、`app/App.vue`、登录/绑定手机号链路、荣誉墙失败态和相关纯逻辑测试。
- API：失效会话的 HTTP 状态码和错误载荷会调整；正常登录、刷新令牌及有效用户业务响应字段保持兼容。
- 数据库：不新增表或字段；现有 OAuth 与用户归属仍是账号身份真源。
