## Context

当前 `playing.vue` 将记分操作建模为选手视角：UI actor 1 表示“我方”，actor 2 表示“对手”，再由 `convertActor` 根据 `isPlayer1` 转换为后端固定的 player1/player2 编号。裁判详情和同步快照固定采用 player1 视角，因此裁判调用现有默认 actor 2 的按钮时，操作会持续落到选手2；斯诺克进球、斯诺克犯规以及局胜按钮均存在这一限制。

后端写接口已经以固定参与方编号处理请求：`MatchScoreReq.Actor` 是得分方，`MatchFoulReq.Actor` 是犯规方，`EndRoundReq.Winner` 是胜方。裁判也已通过统一 capability 校验获得写权限，所以本变更应优先修正移动端的操作建模和界面，不引入新的接口或存储结构。

实现需遵守 UniApp 跨端约束，页面仍通过 `app/api` 调用现有接口；可测试的角色和 actor 映射规则应放入 `app/utils` 纯函数并由 `node:test` 覆盖。

## Goals / Non-Goals

**Goals:**

- 裁判能在四种球类模式下明确对选手1或选手2执行所有适用记分操作。
- 请求中的 actor/winner 始终转换为后端固定的 player1/player2 编号。
- 选手视角的现有相对操作行为和文案保持不变。
- 斯诺克的红球数量、清彩顺序、当前局状态等现有校验继续生效。
- 通过纯逻辑测试和页面结构测试防止裁判模式再次退化为单边记分。

**Non-Goals:**

- 不修改裁判加入、扫码绑定、权限判定或选手只读规则。
- 不新增后端记分接口、WebSocket 消息、数据库字段或迁移。
- 不重新设计整张对局进行中页面，也不改变比赛规则和各操作的分值。
- 不改变撤销、结束整场比赛或排位赛结束确认流程。

## Decisions

### 1. 将“显示身份”与“传输参与方”分开建模

新增一个小型纯函数模块，为给定 viewer role 和目标栏位解析：

- 展示标签：裁判使用“选手1/选手2”，选手继续使用“我方/对手”。
- 请求参与方：裁判目标直接映射为 player1=1、player2=2；选手目标继续通过当前 `isPlayer1` 视角换算。
- 操作语义：得分和局胜传目标受益方，犯规传实际犯规方。

页面事件处理器接收明确的 UI actor 参数，不再让裁判路径依赖默认 `winnerActor = 2` 或固定 `convertActor(2)`。

选择该方案是因为它延续现有后端协议，并把最容易出错的映射变成可独立测试的规则。备选方案是在页面模板中直接写 actor 1/2 分支，但会让四个球种重复角色判断，后续更容易再次产生文案与请求不一致。

### 2. 裁判使用固定双方操作区，选手保留现有单边操作区

当 `viewerRole === 'referee'` 时，操作面板按固定左选手1、右选手2组织：

- 中式八球和美式九球：双方各自展示相同的局胜方式，点击时将对应方作为 `Winner`。
- 九球追分：双方各自展示普胜、小金、大金；犯规入口明确标注犯规方，点击时把犯规方作为 `Actor`。
- 斯诺克：面板提供当前记分对象选择，默认选手1；进球按钮为当前得分方加分。犯规区域独立提供犯规方选择，默认选手1，并将对方获得罚分的结果通过文案明确展示。

选手视角继续展示现有的“给对手计分/对手犯规”等单边操作，降低变更范围并避免改变既有产品行为。

斯诺克采用“选择当前对象 + 共用球按钮”，而不是把整套七球和犯规按钮复制两份，以控制移动端页面长度和模板重复。得分方与犯规方使用独立选择状态，避免切换得分对象时意外改变犯规对象。

### 3. 复用现有写操作与同步链路

`handleAddScore`、`handleFoulByScore`、`handleFoul` 和 `handleOpponentWin` 调整为接收明确目标，并继续使用：

- `buildActionRequest` 生成 `client_action_id` 与 `base_revision`。
- 现有 `matchScore`、`matchFoul`、`endRound` API 门面。
- `applyWriteResponse`、WebSocket 快照和 revision 冲突处理。

成功 Toast 和操作区说明根据角色及实际目标生成，不能再固定显示“对手”或“我方”。这样只改变请求构造和显示，不触碰并发与回放机制。

### 4. 后端仅做契约澄清和针对性回归验证

`.api` 中 actor/winner 的注释改为固定“1=选手1，2=选手2”，以匹配后端真实存储语义。如果修改 `.api`，必须立即运行项目规定的 goctl 命令生成代码；只允许提交由该注释变更产生且必要的生成结果。

后端测试重点验证裁判身份提交 actor/winner 1 和 2 均能命中正确一方。若现有逻辑测试已充分覆盖固定编号和裁判权限，则只补最小缺口，不改写处理逻辑。

### 5. 测试同时覆盖纯映射与模板入口

新增或扩展 `app/tests`：

- 纯函数测试覆盖 player1、player2、referee 三种视角下目标到 API actor 的映射。
- 每种球类至少覆盖裁判对选手1和选手2各一次适用操作。
- 页面结构测试确认裁判分支存在双方入口，且斯诺克得分方和犯规方不是硬编码 actor 2。
- 原有选手视角与只读裁判接管测试继续通过。

## Risks / Trade-offs

- [裁判误选当前斯诺克对象] → 得分方和犯规方选择器持续显示当前选中项，按钮区标题同步显示操作结果归属，成功 Toast 包含选手身份。
- [模板分支增加导致页面复杂] → 仅对裁判增加必要分支，共享操作配置和事件处理器，不重构无关比分、底部按钮和弹窗代码。
- [犯规 actor 被误解为得分方] → 纯函数和处理器使用 `foulingActor` 命名，UI 文案明确“选手X犯规，选手Y +N 分”，并补双向测试。
- [API 注释变更触发大量生成差异] → 修改后立即运行 goctl，检查差异并只保留与契约注释同步直接相关的内容；若生成器不会传播注释，则不手改生成文件。
- [移动端双列按钮过窄] → 局胜和九球追分沿用现有 grid/column 组件并在小屏允许单列或紧凑布局；斯诺克不复制整套球按钮。
