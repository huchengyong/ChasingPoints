## Why

移动端当前在 App 前台恢复、Tab 切换和子页面返回时重复发起大量认证读请求，后端又存在历史全量加载、内存分页、N+1、读接口写副作用和重复统计计算，导致请求数与单次查询成本同时偏高。最新纳入当前 HEAD 的连续赛季生命周期还在在线读取和每分钟 Worker 中多次加载全部赛季，并在换季事务内扫描整季比赛、按用户球种逐个查询段位日志，因此需要在继续扩展数据量前统一建立可观测、可失效、可批量重建的高效读模型与缓存边界。

## What Changes

- 按优先级分批治理移动端重复请求：以认证用户隔离的 Pinia 资源状态、并发请求复用、dirty/TTL/SWR、前台 Bootstrap 和 WebSocket 失效替代无条件 `onShow` 全量刷新；修复排行榜首次双请求、挑战 Tab 重复请求及设置/资料等页面的重复加载。
- 新增面向页面首屏的聚合能力，包括用户 Bootstrap、用户概览、竞技统计概览、H2H 概览、对手候选、赛季首屏概览和首页榜单摘要；通知列表同时返回未读数，并保留部分结果可用及独立分页能力。
- 将 H2H 首屏按已确认方案改为单个 overview 请求，统一返回对手资料、聚合统计、首屏历史和总数，不再对同一月份重复请求不同 page size 的历史接口。
- 建立幂等的比赛参与者读模型和用户竞技统计快照，在比赛结算事务中维护总场次、胜负、连胜、分球种统计、最高分、时长、对手统计、H2H 及当前赛季记录；在线接口不得再通过加载用户全部历史计算这些结果。
- 对局结果页继续展示双方“当前最新”的胜率和最高分：不可变的对局核心结果单独长期缓存，实时用户指标从最新统计快照读取并按快照 revision 组装；结果页与分享链路复用同一结果摘要服务。
- 将近期趋势、对局历史、H2H 历史、对手列表等改为基于参与者读模型的有界索引分页；消除好友、好友申请、挑战、球馆、赛季榜单、裁判历史、公开对局局数等 N+1。
- 清除热路径 GET 的隐式写副作用：规则播种移至 migration/启动初始化，挑战过期移至写入判断或异步任务，段位初始化移至用户初始化/显式修复，赛事对阵生成和成就补偿与纯读取边界解耦。
- 为赛讯现有 Redis 缓存补充客户端缓存，并为共享排行榜、静态规则/术语/地区/段位配置、球馆、历史赛季及已完成对局核心摘要建立有界、可版本失效、Redis 不可用时可回源的缓存；进行中对局、认证、支付、二维码、上传凭证和写操作不得使用普通响应缓存。
- 优化连续赛季生命周期：在线当前赛季解析和每分钟 Worker 使用确定性窗口及索引查询，不重复 `ListAll`；当前赛季记录随比赛结算增量维护；换季只读取赛季范围快照并以批量、幂等方式完成最终排名、挑战归档和通知，不在长事务内扫描全部比赛或执行按用户 N+1 查询。
- 为附近球馆增加边界框/可索引地理预筛选，再计算精确距离；任何在线查询不得依赖非标准、昂贵或无界全表扫描手段。
- 使用项目已有 go-zero、Gorm、MySQL、Redis、Pinia 和 WebSocket 实现，不引入收费或专有基础设施；异步任务必须可重试、幂等、分批且有界，并行查询必须彼此独立且限制并发。
- 建立性能验收基线：统一实际生效的日志配置，使用标准指标记录路由 QPS、P50/P95/P99、响应大小、SQL 次数与耗时、慢查询、缓存命中率和页面首屏请求数。当前 JSON 文件日志变更保留，但 `Stat: false`、空 access log 及两份配置不一致的问题纳入治理。

## Capabilities

### New Capabilities
- `auth-safe-client-read-coordination`: 定义认证隔离的客户端资源复用、并发去重、TTL/SWR、页面生命周期和 WebSocket/前台恢复失效行为。
- `read-api-composition`: 定义 Bootstrap、用户/统计/H2H/赛季概览、对手候选、榜单摘要和通知计数等聚合读接口及部分失败语义。
- `competitive-read-models`: 定义比赛参与者投影、用户统计/H2H/对手/赛季快照、幂等结算更新、批量历史重建及对局结果最新指标语义。
- `shared-read-caching`: 定义公共静态数据、排行榜、球馆、赛讯和已完成对局核心摘要的客户端/Redis 缓存、版本失效、回源及明确禁缓存范围。
- `bounded-read-queries`: 定义在线接口必须使用有界索引分页、批量 JOIN/聚合并消除 N+1、内存分页、历史全量加载和 GET 写副作用。
- `performance-observability`: 定义标准日志与性能指标、配置单一真源以及各阶段上线前后的可量化验收要求。

### Modified Capabilities
- `continuous-season-lifecycle`: 将在线赛季解析、每分钟生命周期协调和换季结算约束为确定性、有界、索引化和快照驱动，并保证当前赛季记录在赛季进行中实时可读。

## Impact

- 移动端：`app/App.vue`、TabBar 页面、用户/统计/H2H/荣誉墙/赛季/通知/挑战/设置等子页面，现有 `user`、`rank`、`notification`、`friendRequest` Store 及新增的活动状态/概览资源状态。
- API 契约：`backend/chasing_points.api` 新增聚合、摘要、静态配置和必要的 revision 字段；修改后必须立即运行 goctl，并同步 `app/api` 门面。
- 后端：`handler -> logic -> model` 读链路、比赛结算、统计服务、赛季生命周期与结算 Worker、WebSocket 用户事件、认证中间件 Context 复用和 Redis 缓存。
- 数据：新增比赛参与者投影及竞技/对手/赛季快照所需表或字段、唯一键和组合索引；历史数据通过按主键/时间游标的可恢复批处理回建，不执行无界一次性加载。
- 运维：统一 `backend/etc/chasing_points-api.yaml` 为实际运行配置真源，澄清或移除漂移的 `chasingpoints-api.yaml`；增加标准性能指标和缓存命中监控。
- 兼容性：保留现有细粒度接口作为过渡和独立分页兜底；聚合接口为加法式扩展，缓存失效或 Redis 故障不得影响核心读写正确性。
