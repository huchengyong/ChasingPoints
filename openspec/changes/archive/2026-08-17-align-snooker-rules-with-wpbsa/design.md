## Context

当前斯诺克记分沿用通用 `score/foul/win` 操作：客户端直接提交整数分值，后端把 `ScoreChange` 同时当作球值、比分增量和单杆统计来源，再从未撤销动作推导红球数量与清彩状态。这一模型无法表达合法未进球、上手切换、自由球、犯规杆中离台的红球及重置黑球，并且 `score` 大于7或小于1时仍可能被接受。

现有对局写链路已经具备可复用基础：`client_action_id` 幂等、`base_revision` 并发控制、`MatchAction` 操作日志、撤销标记、WebSocket 快照及当前局/整场比分分离。本设计保留这些基础，不引入台面坐标或视觉识别，而是由裁判或记分员输入已经判定的击球结果，后端负责验证其规则后果。

API 契约以 `backend/chasing_points.api` 为单一真源，修改后必须立即运行 goctl。移动端页面继续只能通过 `app/api/*.js` 调用接口，可测试规则优先放在后端纯状态机和移动端纯函数中。

## Goals / Non-Goals

**Goals:**

- 让升级后的标准15红球斯诺克对局只能通过合法的球、击球结果和裁判决定改变比分与局状态。
- 明确维护当前击球方、目标球、红球剩余数、上手编号、自由球、清彩和重置黑球状态。
- 使合法未进球、犯规、重打和认输都能结束或保持正确的上手与目标球。
- 让单杆、50+、破百和147只基于后端确认的同一次上手得分计算。
- 保持现有 revision、幂等、撤销、快照和双方视角能力。
- 为既有对局提供明确的兼容边界，不用不完整的历史动作伪造新规则状态。

**Non-Goals:**

- 不通过球位坐标自动判断是否形成斯诺克、是否推杆、跳球或是否尽到最大努力；这些事实由裁判输入。
- 不实现四人斯诺克、六红球、单限时赛等变体。
- 不在本变更中建立完整的台面复位坐标系统；“原位重打”只记录裁判决定，球的物理复位在线下完成。
- 不重构其他三个球种的记分协议。
- 不修改已完成旧对局的历史比分、单杆或排位结算。

## Decisions

### 1. 以规则版本隔离旧记分和新状态机

在 `matches` 增加 `snooker_rules_version`，现有数据保持版本1，具备新规则能力的客户端在创建标准斯诺克对局时显式提交版本2。版本2同时保存 `best_of_frames` 和 `starting_actor`；非斯诺克对局继续使用现有逻辑。

- 创建请求增加显式 `snooker_rules_version` 协商；新客户端提交版本2并同时提交有效赛制，未提交版本字段的旧客户端在兼容窗口内继续创建版本1，避免后端先行发布直接阻断旧 App。
- 版本1继续接受旧页面和旧 `score/foul/endRound` 流程，直至既有进行中对局和兼容窗口内创建的旧客户端对局自然结束。
- 版本2禁止通过通用 `score`、`foul` 和客户端指定胜方的 `endRound` 修改斯诺克状态，统一走新斯诺克动作接口。
- 已有但尚无任何有效记分动作的进行中斯诺克对局可以在迁移时显式升级；已有动作的进行中对局不自动升级。

选择显式版本字段，而不是根据动作内容猜测版本，是为了让回放、撤销、客户端展示和回滚都有稳定边界。备选方案是一次性转换所有历史动作，但旧日志没有上手、未进球和自由球信息，无法可靠转换。

### 2. 使用斯诺克专用动作接口表达一次物理击球

新增两个写入口，并继续复用现有 action id、revision 和快照响应：

1. `POST /api/match/snooker/stroke`
   - `actor`：实际击球方，必须等于服务器状态中的当前击球方。
   - `outcome`：`pot`、`no_score` 或 `foul`。
   - 进球字段：实际入袋红球数、入袋彩球、自由球指定球、自由球是否入袋、真实目标球是否入袋。
   - 犯规字段：4至7分罚分、实际离台红球数、是否判 Foul and a Miss、是否属于可连续警告的原位重打序列、犯规后选择。
   - 犯规后选择限定为 `incoming_plays`、`offender_plays_from_left`、`offender_replays_original`。
   - 当裁判判定犯规后形成斯诺克且由非犯规方从现状击球时，可标记下一杆拥有自由球。

2. `POST /api/match/snooker/frame-action`
   - `action`：`start_respotted_black`、`offer_concession`、`accept_concession`、`reject_concession` 或裁判允许的 `award_frame`。
   - 重置黑球动作指定抽签或协商后的先打方。
   - 选手认输采用提议/接受两步；裁判可记录双方已经接受的认输结果。

通用接口继续服务其他球种。选择专用接口而不是继续给 `MatchScoreReq` 叠加大量可选字段，是为了避免“任意分值”和“球值”继续混为一谈，也让每种动作的字段组合可以在后端集中校验。

### 3. 在现有 MatchAction 上存储版本化斯诺克事件

继续使用 `match_actions`，不新增第二套操作日志表：

- `ActionType` 使用 `snooker_stroke`、`snooker_frame_action`、`round_start`、`win` 等明确类型。
- `ScoreChange` 只保存该事件实际产生的净得分或罚分，供列表展示，不再用于推断球和规则状态。
- `ExtraData` 保存带 `version: 2` 的结构化 JSON，包括击球结果、实际离台球、自由球、犯规决定、服务器分配的 `visit_no` 和局结束原因。

新增严格的 JSON 编解码 helper；未知版本或缺少必填字段时回放失败并拒绝继续写入，而不是静默忽略。使用现有 JSON 字段可减少迁移和事务复杂度；若后续需要按击球细节做数据库查询，再独立评估结构化列。

### 4. 用确定性状态机重放当前局

版本2的 `SnookerRoundState` 至少维护：

- `phase`：`reds`、`color_after_red`、`colors`、`respotted_black_pending`、`respotted_black`、`ended`。
- `ball_on`：`red`、`color_choice`、黄/绿/咖啡/蓝/粉/黑。
- `striker`、`starting_actor`、`visit_no`、`current_break`。
- `reds_remaining`、已清彩球、自由球可用状态、D区手中球状态。
- 连续 Miss 次数、警告状态、局胜方和结束原因。

核心转移规则：

- 每局由预定开球方从红球为目标球开始；下一局开球方固定轮换。
- 红球为目标球时，可在同一杆打进一颗或多颗真实红球，每颗1分并减少对应红球；得分后进入自选彩球。
- 自选彩球杆结束后：仍有红球则回到红球；已无红球则进入黄球。即使该杆合法但未进球，也必须完成此转移并结束上手。
- 顺序清彩只接受黄、绿、咖啡、蓝、粉、黑；真实目标彩球合法入袋后才前进到下一颗。
- 合法未进球结束当前上手并切换击球方；犯规根据非犯规方的选择决定下一击球方和是否恢复原目标球。
- 犯规杆不给犯规方任何入袋分，但真实离台红球仍减少；罚分只记给非犯规方。
- 每次开始新的上手由服务器递增 `visit_no`，单杆只在同一局、同一 actor、同一 visit 内累计。

状态机作为纯函数接收前一状态和单个已验证事件，返回新状态及比分增量；服务层在事务中重放并写入 Match、Round 和 Action。选择确定性重放而不是在多个 handler 中手工增减，是为了让撤销、冲突重试、快照和统计使用同一规则源。

### 5. 自由球由裁判判定，后端验证计分后果

系统不根据球位判断自由球，只接受裁判在犯规结果中标记 `free_ball_awarded`。下一杆如使用自由球，必须声明指定球：

- 指定球不能是当前真实目标球，并取得当前目标球的分值。
- 指定球入袋后复位，不减少真实红球或清彩目标球。
- 红球为目标球时，指定自由球和真实红球同时合法入袋，每颗各计1分；只有真实红球减少 `reds_remaining`。
- 顺序清彩时只打进指定自由球不会推进真实目标彩球；真实目标彩球同时合法入袋时才推进。
- 要求犯规方重打或原位重打时，自由球资格失效。

该模型覆盖记分所需后果，同时避免引入球位几何。

### 6. Foul and a Miss 使用裁判输入的资格标志维护序列

犯规事件可由裁判标记 `foul_and_miss`。只有同时标记“具备中央整球直线击打条件”并选择原位重打时，后端才累计连续序列：

- 第二次符合条件的失败后，快照进入已警告状态。
- 警告后从同一原位再次符合条件地失败，系统允许并执行判给对手本局。
- 改为从现状击球、成功击中目标球、结束该局或取消原位重打时，连续序列清零。

系统验证序列一致性，但“是否判 Miss”和“是否具备整球直线条件”仍由裁判负责。这样可以实现官方记分后果，又不伪装成自动裁判。

### 7. 最后黑球和重置黑球由状态机自动控制

顺序清彩的最后黑球发生第一次合法入袋或犯规后：

- 分数不相同则立即结束当前局并生成 `MatchRound`，胜方由最终局分确定。
- 分数相同则进入 `respotted_black_pending`，不允许开始下一局。
- 裁判或双方通过 `start_respotted_black` 指定先打方后，状态进入 `respotted_black`、黑球为唯一目标球、母球为D区手中球。
- 重置黑球阶段第一次合法黑球得分或犯规立即结束本局。

版本2不再由客户端根据当前比分提交 `Winner`。局结束事件、Round、整场局比分和 WebSocket 消息在同一事务中生成。

### 8. 对局赛制和认输由后端判定

版本2标准斯诺克创建请求增加：

- `best_of_frames`：正奇数。
- `starting_actor`：1或2，表示抽签或双方约定后的首局开球方。

所需胜局为 `best_of_frames/2 + 1`。每局结束后任一方达到目标即自动完成整场比赛；未达到目标时才允许开始下一局。版本2不得通过普通“结束本场”产生平局。

系统根据当前目标球、红球剩余和自由球状态计算台面可得分。当落后方需要罚分才能反超时才允许提出本局认输；提议只有在对方接受后生效。整场认输或裁判判罚直接把尚需胜局判给对方，并记录结束原因。普通“开始下一局”不再隐式把未结束的当前局判给领先方。

### 9. 快照兼容旧字段并增加权威斯诺克字段

版本2快照增加 `snooker_rules_version`、`snooker_phase`、`snooker_ball_on`、`snooker_striker`、`snooker_visit_no`、`snooker_current_break`、`snooker_reds_remaining`、`snooker_free_ball_available`、`snooker_cue_ball_in_hand`、`snooker_miss_warning_active` 和重置黑球/认输状态。

为减少页面和观战链路一次性改动，现有 `red_ball_count`、清彩字段继续返回，但由新状态派生；版本2页面以新字段为准。WebSocket、HTTP写响应、对局详情和公开观战使用同一快照构造函数。

### 10. 撤销后通过回放重建，而不是反向猜测

撤销仍只撤销最近一个可撤销事件。对于版本2：

- 标记动作撤销后，从当前局开始事件重放所有有效事件。
- 重新计算当前局比分、局状态、上手和单杆。
- 若撤销的是结束局的事件，同时删除对应 Round、回退整场胜局和比赛完成状态。
- 若撤销使比赛从已完成恢复为进行中，现有排位/成就结算不得通过普通撤销直接回滚；已完成整场比赛继续禁止撤销。

这比为自由球、红球离台、Miss 和重置黑球分别维护逆操作更简单可靠。

### 11. 单杆与奖励按 visit 聚合

版本2的最高单杆和奖励从合法 `snooker_stroke` 事件读取服务器写入的 `visit_no`：

- 只累计该 visit 内击球方的合法得分。
- 犯规罚分不计入任何单杆。
- 合法未进球、犯规或击球方切换结束 visit。
- 50+、破百和精确147按每个完成 visit 计算；合法自由球产生的更高单杆仍展示真实分数，但不伪装为 `break_147`。
- 排位奖励只使用已完成局中的版本2事件；非法或无法解码事件使结算失败而不是降级为任意 `ScoreChange`。

版本1已完成对局继续使用旧统计，避免重写历史。

### 12. 规则文案通过迁移更新

修正 `GetDefaultRulesContent`，并新增迁移按 `(category, content_type, title)` 更新现有斯诺克规则行，至少覆盖：

- 开球不要求红球碰库或入袋。
- 同时首碰两颗红球以及自由球与目标球的合法例外。
- 斯诺克以目标球两个极边是否可被直线击中判断。
- 自由球和理论最高155分说明。

只改 seed 不会更新已有数据，因此迁移与 seed 必须同时提交。

## Risks / Trade-offs

- [斯诺克动作字段较多，客户端容易提交互相矛盾的组合] → 按 `outcome` 建立严格的后端组合校验，并让移动端只从当前快照生成合法选项。
- [版本1和版本2并存增加分支] → 仅在斯诺克入口按单一版本字段分流，不在通用 helper 中散布猜测逻辑；版本1只用于存量进行中对局。
- [ExtraData JSON 难以查询] → 当前需求全部通过按对局顺序回放满足，先避免新增动作明细表；后续出现跨对局明细查询再迁移。
- [裁判对自由球或 Miss 的事实判断错误] → 页面明确这些是裁判判定，后端只验证状态一致性和记分结果，并保留撤销。
- [规则状态机缺陷会影响奖励] → 状态转移、回放、撤销和奖励共享同一事件解释器，并用 WPBSA 场景建立表驱动测试。
- [双端同时写导致击球方过期] → 继续使用 `base_revision`，冲突时返回完整权威快照，客户端不得本地猜测重放；同一 `client_action_id` 必须同时绑定规范化动作内容，不能把不同击球静默当作重试。
- [旧客户端不认识版本2创建字段] → 通过显式规则版本协商保留兼容窗口；旧请求不自动升级，新客户端统一显式请求版本2。版本2对局仍要求参与端具备版本2能力，正式开放前需配合最低客户端版本策略。
- [全量后端回滚无法识别已创建的版本2对局] → 回滚优先回滚移动端并保留版本2后端处理，若必须回滚后端则先停止创建新斯诺克对局并处理所有版本2进行中比赛。

## Migration Plan

1. 新增兼容性数据库迁移：为 `matches` 增加规则版本、总局数和首局开球方字段；现有记录保持版本1。
2. 先发布可识别显式版本字段的兼容后端：旧请求继续创建版本1，新客户端请求版本2时才启用新状态机。
3. 更新默认规则 seed，并通过同一批或后续迁移修正现有 `rules_content` 行。
4. 发布移动端版本2创建、记分、犯规决定、重置黑球和认输界面；所有移动端创建入口显式提交版本2，旧进行中对局根据快照版本继续显示旧面板。
5. 配合最低客户端版本或灰度开关观察版本2动作解码、revision 冲突、撤销和结算错误；确认支持版本2的参与端覆盖率后，再评估停止版本1新建，停止动作不属于本变更。
6. 回滚移动端时保留后端版本2路由；数据库新增列和事件不回删。只有在不存在版本2进行中对局时才允许回滚到不识别版本2的后端。

## Open Questions

无。标准规则基线固定为 WPBSA 2024/25，六红球及其他变体另行提案。
