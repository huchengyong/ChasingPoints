## Context

现有 `seasons` 表以 `status = 0/1/2` 表示未开始、进行中和已结束，`SeasonRolloverWorker` 每分钟扫描已到期的活动赛季，调用 `SeasonSettlementService` 归档挑战、生成赛季记录与称号，并尝试激活一条已经存在且开始日期已到的待开始赛季。Worker 不负责创建赛季，仓库也没有生产可用的赛季管理入口或初始化数据，因此开发和生产接口目前都可能返回 `season: null`。

有效排位完成后仍会写入段位日志与 `achievement_progress_events`。生涯成就聚合全部事件，而赛季挑战、赛季记录、报告和称号按赛季日期窗口重新查询。没有赛季覆盖的事件因此会推进生涯和段位，却永远不进入赛季资产；同时这些段位变化还可能成为下一赛季的起始分，造成口径不一致。

当前时间范围实现也存在多种边界写法：部分使用结束日期次日的排他边界，部分直接使用 `end_date` 当天零点并采用 `<=`。连续赛季必须先统一这些口径。实现仍需遵守 API 契约先改 `backend/chasing_points.api` 并立即运行 goctl、线上 schema 只由 migrations 管理、移动端页面只通过 `app/api` 请求后端等仓库约束。

## Goals / Non-Goals

**Goals:**

- 赛季功能启用后，从配置的生效起点开始让每个有效赛季事件恰好落入一个连续赛季窗口。
- 只配置一次赛季起点、初始编号、周期和时区，系统自动建立当前赛季并持续准备下一赛季。
- 多实例、重启和 Worker 延迟情况下仍可幂等收敛，不产生重复赛季、重复结算、重复称号或时间空窗。
- 统一比赛、赛事、段位日志、挑战快照、赛季记录和报告的时间边界。
- 安全修复功能启用后已经发生但尚无赛季覆盖的数据，并提供 dry-run 审计结果。
- 让 API 和移动端区分“尚未启用”“正常进行”和“数据不可用”，不再把缺失当前赛季统一解释为间歇期。

**Non-Goals:**

- 不修改三项赛季挑战的 Key、门槛或奖励语义。
- 不重置或降低生涯成就、称号、历史荣誉和当前佩戴状态。
- 不在本变更中执行段位软重置，也不启用 `rank_reset_ratio` 的计算。
- 不建设管理后台赛季编辑器、营销主题赛季或自定义单届规则。
- 不为比赛、段位日志和成就事件新增持久化 `season_id`；本期继续使用不可重叠的权威时间窗口归属。
- 不重做当前赛季排行榜的实时计算方式。

## Decisions

### 1. 使用一次性配置驱动连续自然月赛季

新增后端赛季生命周期配置，包含：是否启用、锚点日期、初始赛季编号、每季包含的自然月数和业务时区。锚点必须是业务时区中的月初，周期必须为正整数月，默认时区为 `Asia/Shanghai`、默认周期为一个自然月。第 `n` 个窗口名称确定性生成为 `S{initial_number+n}`，开始日期由锚点按周期递增，结束日期为下一窗口开始日期的前一天。

该方案保留现有 `seasons.start_date/end_date/name/status` 结构，不增加单独的策略表或每届后台配置。生产环境只需在首次启用时确认锚点和编号，后续名称及日期可重复计算。

**替代方案：** 每届由管理员提前创建。它能支持营销化日期，但当前没有管理入口，且遗漏一届就重新产生数据空窗，因此不采用。固定 28 天周期虽然长度一致，但日期持续漂移、用户理解成本更高，也与现有按自然月编写的换季测试和展示不一致。

### 2. 赛季时间窗口是数据归属真源，status 是结算工作流状态

统一将数据库中的日期解释为业务时区下的半开区间：

```text
[start_date 00:00:00, end_date + 1 day 00:00:00)
```

相邻赛季必须满足 `next.start_date = current.end_date + 1 day`。有效排位以 `COALESCE(end_time, match_time)` 归属，赛事与成就指标使用既有 `occurred_at`，段位日志使用 `effective_at`。跨越边界的对局按完成时间归属新赛季。

读取“当前赛季”时使用包含当前业务时间的权威窗口，而不是仅依赖 `status = 1`；Worker 负责把持久化 status 最终收敛为历史 `2`、当前 `1`、未来 `0`。这样短暂的 Worker 延迟不会让客户端进入无赛季状态，结算状态也不会改变历史事件归属。

**替代方案：** 在每个事件上写入 `season_id`。它能冻结归属，但需要修改比赛、赛事、段位和成就多条写入链路及历史回填；当前事件时间已经足以确定唯一窗口，先统一窗口更简单。

### 3. 生命周期服务确定性补齐排期并用数据库约束收敛并发

新增共享 `SeasonLifecycleService`，根据配置和指定时间执行：

1. 配置未启用或当前时间早于锚点时返回 `not_started`，不创建记录。
2. 从锚点开始确定性生成截至当前窗口及至少一个未来窗口。
3. 复用起始日期一致的既有记录；缺失窗口幂等插入。
4. 检测重叠、重复起点或与确定性排期冲突的既有记录，停止自动修改并报告 `unavailable`，不得猜测或覆盖历史日期。
5. 将 status 按当前时间和结算进度收敛，但不撤销已完成结算。

为 `seasons.start_date` 增加唯一索引，并继续使用赛季行锁、结算唯一键和条件状态更新，使多个服务实例同时运行时至多创建一条同日起点赛季。

**替代方案：** 只在 migration 中预插入若干未来赛季。它只能把忘记配置的问题推迟，不能长期保证连续性，因此不采用。

### 4. Worker 先确保排期，再按时间顺序追赶所有到期结算

`SeasonRolloverWorker.RunOnce` 先调用生命周期服务补齐当前和下一窗口，再按开始日期顺序处理所有已经结束但尚未完成结算的赛季，直到达到当前有效窗口。每一届继续使用独立数据库事务：归档挑战、生成/合并赛季记录、发放幂等称号、关闭旧赛季并启用下一赛季；任一步失败则整届回滚并在下次运行重试。

普通准时换季保留现有通知。显式历史修复模式不创建未读换季通知、不发送 Push/WebSocket，也不把修复执行时间冒充业务获得时间。Worker 因短暂故障延迟后恢复时，新赛季挑战直接按既定窗口查询已发生事件，因此不会从恢复时刻错误地重新从零开始。

### 5. 所有赛季查询复用一个规范窗口 helper

建立共享的业务时区日期解析和 `startInclusive/endExclusive` helper。当前赛季响应额外返回 RFC3339 的 `start_at` 与 `end_at_exclusive`，移动端优先用这两个权威时刻计算进度和剩余天数；旧后端响应才按默认 `Asia/Shanghai` 日期兼容解析。替换以下路径中直接传递 `season.EndDate` 或各自计算次日的逻辑：

- 当前赛季解析与排行榜默认赛季；
- 赛季挑战实时进度和归档快照；
- 赛季结算的有效比赛与段位日志；
- 赛季报告中的趋势、胜率和本赛季解锁成就；
- `RankRebuildService` 的比赛归季与赛季记录重建。

这项统一既修复空窗，也消除结束日期当天大部分时间可能被部分查询排除的风险。

### 6. 使用专用 dry-run/execute 修复入口处理上线数据

新增赛季生命周期修复命令，复用生命周期服务并输出：配置窗口、待创建赛季、冲突窗口、待结算赛季、覆盖的事件与用户数量、预计挑战快照/赛季记录/称号数量。`--dry-run` 不写任何数据；正式执行幂等创建缺失窗口并静默结算已经结束的窗口。

锚点之前的历史数据继续只属于生涯资产，不强行虚构历史赛季。锚点之后的数据通过补齐窗口自动获得赛季归属；当前窗口的挑战无需搬迁事件即可即时反映已有进度。

**替代方案：** 修改事件时间或复制进度事件。该方案会破坏生涯成就幂等键并可能重复发奖，因此不采用。

### 7. API 增加显式 season_state，旧字段保持兼容

在当前赛季响应和本人荣誉墙响应中增加 `season_state`：

- `not_started`：配置未启用或尚未到锚点；
- `active`：存在覆盖当前业务时间的有效窗口；
- `unavailable`：已到启用时间但排期缺失、冲突或查询失败。

`season/current` 在 `active` 时继续返回原有 `season`；另外两种状态返回空 season。荣誉墙在赛季数据不可用时仍返回生涯成就和历届荣誉，不因赛季子域问题使整页失败。字段采用加法式扩展，旧客户端仍可读取原结构。

新客户端分别显示“赛季尚未开启”和“赛季数据更新中”；正常连续模式不再展示“赛季间歇中”。

### 8. 连续换季只重置赛季挑战，不改变段位与永久资产

新窗口的三项挑战通过新的时间范围自然独立累计，生涯成就继续聚合全部事件。换季和修复不得降低当前段位、应用 `rank_reset_ratio`、撤销称号或改变佩戴状态。段位软重置需要独立规格和迁移评估后再启用。

## Risks / Trade-offs

- **[错误锚点会把事件归入错误赛季]** → 正式执行前强制 dry-run，输出每个窗口及覆盖事件数量；已有冲突时拒绝自动修正。
- **[多实例同时补齐赛季产生重复记录]** → 为 `start_date` 增加唯一约束，并使用事务、行锁和条件更新收敛。
- **[服务长时间停机后一次追赶多届结算耗时]** → 按赛季逐事务处理并保持幂等；失败后从首个未完成赛季继续，不回滚已完成届次。
- **[修复历史结算造成通知或称号洪峰]** → 修复模式静默通知，称号使用现有来源唯一键，报告预计和实际新增数量。
- **[自然月长度不同导致挑战可用天数略有差异]** → 保持用户易理解的月度边界；本变更不调整挑战门槛，后续根据真实完成率另行评估。
- **[旧客户端仍把空 season 显示为间歇期]** → API 保持兼容但优先发布新客户端文案；正常启用后 active season 将使旧客户端也不进入该兜底。
- **[status 与时间窗口短暂不一致]** → 读取按时间窗口解析，Worker 在启动及周期任务中立即协调 status，结算继续由唯一状态记录保护。

## Migration Plan

1. 修改 `backend/chasing_points.api` 增加 `season_state`，立即运行 goctl，并先部署可读取新字段但尚未启用自动生命周期的后端。
2. 新增 migration，为 `seasons.start_date` 建立唯一约束和必要查询索引；上线前检测重复起点，Down 只移除新增索引，不删除赛季或用户资产。
3. 增加赛季生命周期配置、窗口 helper、生命周期服务、修复命令和 Worker 协调逻辑，配置默认保持未启用。
4. 在目标环境设置锚点、初始编号、周期和时区，运行修复命令 dry-run，核对生成窗口、事件覆盖、冲突和预计结算结果。
5. 执行正式修复，确认当前窗口及下一窗口存在、已结束窗口结算完成，并重复执行验证零新增或仅有预期的状态收敛。
6. 启用连续赛季 Worker，发布识别 `season_state` 的移动端，观察一个完整边界的归档、自动续期、通知和挑战进度。
7. 回滚时先关闭生命周期配置；保留已生成赛季、结算记录、挑战快照和荣誉，旧后端仍可读取其中 `status = 1` 的赛季。API 新字段和数据索引可安全保留，避免通过删除资产回滚。

## Open Questions

- 正式环境的锚点日期和初始 S 编号需要在执行 dry-run 前确认；这属于上线参数，不阻塞通用能力实现。
- 是否在未来启用段位软重置及其与会员段位权益的关系，需要单独产品与数据方案，本变更明确不处理。
