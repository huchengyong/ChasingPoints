## Context

当前公开用户界面由两套技术栈承载：`app/` 是同时输出 App 与微信小程序的 UniApp Vue3 客户端，`website/` 是 Nuxt 3 官网。两端已经形成金色品牌、高价值暖黑卡片和大圆角 CTA 的共同方向，但标准仍依赖页面作者手工保持：

- App 的原生主题入口分布在 `theme.json`、`App.vue`、`uni.scss` 和 `utils/theme-application.js`，所有页面已通过 `usePageTheme` 接入亮暗主题，但大部分页面仍使用本地 Sass 变量或硬编码颜色。
- App 的欢迎、登录、首页和“我的”较接近暖金品牌，排行榜、部分对局、反馈、赛季、社交、赛事和球馆页面仍存在 `#101922`、`#1e293b` 等冷蓝黑表面。
- 官网内部视觉较一致，但品牌色、文字色、圆角和 CTA 渐变重复写在多个 scoped style 中，没有可验证的语义 Token。
- UniApp 必须兼容 App 与微信小程序，不能依赖小程序不支持的通配选择器，也必须保留原生按钮、安全区和系统导航栏约束。

本次变更是跨 `app/`、`website/` 和仓库文档的视觉基础设施与迁移工作。它不改变页面信息架构、业务流程或接口。

## Goals / Non-Goals

**Goals:**

- 将当前品牌语言沉淀为仓库根级 `DESIGN.md`，成为官网与 App/小程序 UI 的规范入口。
- 建立跨端同名、分端取值的语义 Token，让品牌色、表面、文字、边框、状态色、圆角、阴影和间距有明确角色。
- 让官网、App 欢迎/登录、主 Tab、高频子页面和现存冷蓝黑旧页面遵循同一暖金视觉语言。
- 保持 App 与小程序共用一套页面样式，并保留 Web 与 UniApp 在尺寸、响应式和系统控件上的必要差异。
- 通过静态契约测试和人工视觉检查防止规范回退。

**Non-Goals:**

- 不修改 `admin/` 管理后台。
- 不新增跨 Nuxt 与 UniApp 共享的运行时组件库、npm 包或构建期 Token 生成器。
- 不重做导航结构、页面布局、业务文案、交互流程、图标资产或数据可视化内容。
- 不新增官网深色模式。
- 不追求官网与移动端像素级一致；统一的是品牌语义和组件层级。

## Decisions

### 1. 根级 `DESIGN.md` 是人类可读的唯一规范入口

在仓库根目录新增 `DESIGN.md`，范围只包含 `app/` 与 `website/`。文档必须包含：

- 适用范围与非适用范围
- 品牌原则与“金主绿辅”语义
- 颜色 Token 与使用禁区
- 亮色、客户端暗色主题
- 字体层级、间距、圆角、阴影
- 按钮、卡片、表单、标签、导航、弹层、空态、加载态和骨架屏
- 响应式、安全区、触控尺寸、对比度、禁用态和动效规则
- App/小程序与官网的单位和平台映射
- 新页面验收清单

`app/AGENTS.md`、`app/GEMINI.md` 和 `website/AGENTS.md` 将引用该文档，避免规范成为无人发现的孤立文件；`app/AGENTS.md` 与 `app/GEMINI.md` 必须保持同步。

**替代方案：**分别在两个子项目维护独立设计文档。该方案会复制品牌规则并增加漂移风险，因此不采用。

### 2. 共享语义名称，但不共享运行时代码

两端使用相同语义名称，分别在现有样式入口实现。首批核心 Token 如下：

| 角色 | 亮色 | 客户端暗色 | 用途 |
|---|---|---|---|
| `brand-primary` | `#E0AE12` | `#E0AE12` | 功能主操作、选中态 |
| `brand-strong` | `#C69200` | `#F0C542` | 品牌文字、重点数字 |
| `brand-gradient-start` | `#D9A617` | `#E0AE12` | 营销/重点 CTA 渐变 |
| `brand-gradient-end` | `#BB8400` | `#A97500` | 营销/重点 CTA 渐变 |
| `brand-tint` | `rgba(224, 174, 18, 0.14)` | `rgba(224, 174, 18, 0.20)` | 轻强调背景 |
| `surface-page` | `#F7F4EC` | `#141109` | 页面底色 |
| `surface-card` | `#FFFFFF` | `#1E180D` | 卡片、弹层 |
| `surface-subtle` | `#FAF8F2` | `#241D10` | 次级区域、输入框 |
| `text-primary` | `#231C0B` | `#FFF7E1` | 主文字 |
| `text-secondary` | `#6E6242` | `#D7C89B` | 辅助文字 |
| `text-muted` | `#9A8C67` | `#9F926E` | 弱提示 |
| `border-default` | `#E9E2CF` | `#3A2E16` | 卡片、输入框边界 |
| `success` | `#18B05B` | `#22C55E` | 成功、在线、正向状态 |
| `warning` | `#F97316` | `#F97316` | 警告 |
| `danger` | `#EF4444` | `#EF4444` | 错误、破坏性操作 |
| `info` | `#3B82F6` | `#60A5FA` | 信息提示 |

冷 Slate 色仍可用于数据图表、媒体遮罩或明确的信息语义，但不得继续作为页面、卡片、输入框或主要文字的基础色。主品牌按钮文字统一使用 `#FFFFFF`。

映射方式：

- App：在 `App.vue` 的 `page` 与 `.dark-mode` 中提供 `--ui-*` CSS 变量；`theme.json` 继续负责原生主题替换；`utils/theme-application.js` 负责运行时导航栏和 TabBar；`uni.scss` 只保留 UniApp 默认变量和必要的编译期别名。
- 官网：在 `website/assets/styles/main.css` 的 `:root` 中提供同名 `--ui-*` 变量，组件通过变量消费共享视觉角色。
- 通过测试验证关键 Token 在各入口保持一致，而不是引入跨项目 JSON 生成器。

**替代方案：**新增仓库级 Token JSON 并由两端构建时生成代码。当前项目没有共享包或生成链路，这会增加构建复杂度，暂不采用。

### 3. 统一组件语义，不建设全量通用组件库

`DESIGN.md` 将规定组件状态和视觉角色，现有页面优先通过 Token 与少量重复样式收口。只有已经在多个位置重复且模板结构稳定的模式才提取共享实现，避免为单次迁移引入通用组件框架。

关键规则：

- 普通主操作使用实色 `brand-primary`；官网营销 CTA、欢迎页和高价值入口可使用品牌渐变。
- 绿色只表达微信登录、成功、进行中、在线和正向变化，不再承担普通品牌 CTA。
- 普通卡片使用 `surface-card + border-default`；高价值身份、荣誉或重点信息可使用暖黑金表面。
- 输入框、筛选 Chip、标签、空态、加载态和禁用态必须使用语义 Token，不得各自创建新的中性色体系。
- App 自定义按钮继续遵守 `margin: 0`、隐藏 `button::after`、`line-height` 与高度一致、`[disabled]` 覆盖和底部安全区规则。
- 官网共用 CTA、卡片和段落标题可通过全局基础类或现有组件收口；不为单一页面新增抽象。

### 4. 采用分阶段页面迁移，先基础再高频再全量审计

迁移顺序固定为：

1. 建立 `DESIGN.md`、两端 Token 和契约测试。
2. 官网共享外壳与复用组件：Header、Hero、Feature、Scenario、Download、FAQ、Footer、PageHero、LegalArticle 及相关页面局部样式。
3. App 入口与主 Tab：welcome、login、index、match、social、user、ranking，以及三个共享业务弹层。
4. 清理已知冷蓝黑页面：ranking、feedback、matchResult、playing、season report、friend homepage、PK report、tournament create/index、notification、rank explain、reputation、venue submit 等。
5. 对全部 `pages.json` 注册页面执行颜色角色、圆角、按钮、空态、加载态和暗色表面审计，修复剩余偏差。
6. 在 App、微信小程序和官网桌面/移动视口执行人工视觉验收。

迁移只调整视觉层；模板结构只有在消除重复组件状态所必需时才修改。

### 5. 自动化只检查可客观判定的契约

新增或扩展测试检查：

- 所有 App 注册页面继续使用共享主题 Hook，并具备亮暗表面。
- `theme.json`、App CSS 变量、运行时导航/TabBar 的核心颜色一致。
- 已知旧冷蓝黑值不得作为 App 页面和卡片背景重新出现；确需用于媒体遮罩或图表时使用明确白名单。
- 官网共享品牌、中性色和圆角必须从 `main.css` Token 获取，已迁移组件不得重复写核心品牌字面量。
- 根级 `DESIGN.md` 存在并包含必要规范章节。

测试不尝试判断“是否好看”。最终验收仍需要人工检查欢迎到首页链路、所有主 Tab、典型列表/详情/表单/弹层、客户端亮暗主题和官网响应式布局。

### 6. 不改变业务和平台行为

样式迁移不得改变路由、接口调用、页面生命周期、表单校验、登录流程或 WebSocket 行为。App 和小程序继续共用模板；只允许通过条件编译保留平台原生限制，不创建平台专属品牌分支。

## Risks / Trade-offs

- **[范围较大，容易产生视觉回归]** → 按基础、官网、主 Tab、旧页面、全量审计分批实施，每批运行现有测试并执行典型页面人工检查。
- **[CSS 变量在不同 UniApp 目标上的表现可能不同]** → 保留 `theme.json`、`uni.scss` 和现有页面主题 Hook，分别在 App 与微信小程序构建/预览验证，不使用复杂的变量计算。
- **[将所有绿色机械替换为金色会破坏状态语义]** → 以元素角色而非色值做迁移，成功、进行中、在线和微信登录继续使用绿色。
- **[过度抽象会扩大改动]** → 不建设跨端组件库，只提取已重复且稳定的视觉模式。
- **[文档与代码后续漂移]** → 子项目知识库引用 `DESIGN.md`，并用契约测试覆盖核心 Token 和禁用旧表面。
- **[静态检查可能误报图表或遮罩颜色]** → 检查聚焦背景/表面声明，并提供小范围、带原因的白名单。

## Migration Plan

1. 记录迁移前的核心页面截图或人工检查基线，并运行 App、官网现有测试。
2. 新增根级 `DESIGN.md` 和两端语义 Token，不立即删除兼容别名。
3. 迁移官网复用组件并运行 `npm run test`、`npm run build`。
4. 迁移 App 入口、主 Tab、共享弹层并运行 `node --test tests/*.test.mjs`。
5. 按已知旧冷色页面清单迁移子页面，再对全部注册路由做静态审计和人工检查。
6. 删除本次迁移后不再使用的局部颜色变量和重复样式，仅清理本次产生的孤儿。
7. 完成 App、微信小程序、官网移动端和桌面端视觉验收。

回滚时可按阶段恢复对应样式提交；本变更没有数据迁移、接口兼容或不可逆操作。
