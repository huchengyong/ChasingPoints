## Decisions

### D1：接口只返回 `vip_level`，头像框由客户端按上下文段位选择

公开接口统一加一个可选整数 `vip_level`：0 表示无，1–5 表示有效会员的成长等级。头像框不由服务端返回，客户端用同一位置已有的 `rank_level` 选框，并用现有 `resolveCdnAssetUrl` 转成 CDN 地址。

- **排行榜、好友：** 已有 `rank_level`，只加 `vip_level`。
- **对局详情：** 加 `my_vip_level`、`opponent_vip_level`。同时加 `my_rank_level`、`opponent_rank_level`，取该场球种的当前段位，用于选头像框。这四个字段与胜率一起属于「当前最新指标」。
- **分享数据：** 加 `my_vip_level`、`opponent_vip_level`、`my_rank_level`、`opponent_rank_level`。
- **约球：** 加 `from_vip_level`、`to_vip_level`。约球卡片没有段位，只展示 VIP 标识。

备选方案是服务端返回完整的 `member_badge` 对象（含框图地址、档位名）。没有采用，原因有两点：服务端会硬编码客户端资源路径，与现有 CDN 解析重复；档位样式属于展示层，原生 iOS 接入时按规格表实现即可。

### D2：后端新增批量解析会员档位的共享读取

在 `backend/internal/logic/` 新增会员展示读取，对外暴露 `ResolveVipLevels(svcCtx, userIDs, now) (map[int64]int, error)`。返回值只含有效会员，非会员不在结果中，调用方读取时按 0 处理。实现固定两次查询（每批最多 500 个用户，超出才增加）：

1. 按 id `IN` 读取 `users.member_expires_at`。
2. 只对有效会员按 `user_id IN` 读取 `member_growth_profiles.growth_points`，用 `ResolveMemberGrowthLevelWithRules` 按当前成长规则换算等级。规则复用 `MemberRightsConfigService.GetConfig()` 的运行时缓存。没有档案按 1 处理。

不直接读取 `growth_level` 列：该列只在发放成长值时更新，后台调整门槛后会和会员中心（按成长值实时换算）不一致。

各列表与详情接口在组装阶段调用一次。出错时由调用方记录日志并按 0 返回其余数据，因为会员标识只是装饰信息，不应拖垮排行榜或好友列表。

单人或双人场景（对局详情、分享、约球）复用同一函数，不另写单用户查询。

### D3：排行榜共享缓存直接包含 `vip_level`

`vip_level` 在构建共享载荷时解析，随载荷缓存 20 秒。`my_ranking` 是按用户单独组装的，也在组装时解析。会员购买与到期不额外触发榜单版本失效，接受最多一个 TTL 的延迟，满足规格中「一个共享榜单缓存周期内反映」的要求。

查询开销：

- 共享载荷冷加载时，榜单行（前三名与列表）共多 1 次用户查询；有效会员存在时再多 1 次成长值查询，成长规则配置走运行时配置缓存。
- 已登录请求的 `my_ranking` 每次多 1 次用户查询，本人是有效会员时再多 1 次。缓存命中的请求因此从 3 次查询变为 4 次。
- 查询次数不随行数增长，由 `ResolveVipLevels` 保证。

备选方案是缓存 `member_expires_at` 并在每次请求时判断。在 TTL 只有 20 秒的前提下收益很小，暂不采用。以后如果 TTL 显著变长，再改为这种做法。

### D4：对局长期核心缓存不含会员字段

对局详情与分享数据中的会员和段位字段，放在现有「当前最新指标」组装步骤里，与胜率、最高分一起读取。不进入按 match id 长期缓存的核心摘要，遵循 `shared-read-caching` 的现有要求。

### D5：外观档位映射与 VIP 标识组件放在客户端

新增 `uniapp/utils/member-identity.js` 纯函数，输入 `vipLevel` 与 `rankLevel`，输出：

- `showBadge`
- `tier`：`standard` / `advanced` / `premium`
- `badgeText`：例如 `VIP3`
- `frameUrl`：没有段位或不是会员时为空

本人「我的」页现有的头像框与标签逻辑改用同一函数，旧的 `resolveMemberRankAvatarFrame` 收敛进去。

新增 `uniapp/components/memberAvatar.vue`，包含头像、头像框和 VIP 标识，各页面按尺寸 prop 复用，不在每页复制。标识样式遵循 `DESIGN.md`「金主绿辅」与「高价值信息可用暖黑金表面」：

| 档位 | 成长等级 | 标识样式 |
| --- | --- | --- |
| 标准 | Lv1–Lv2 | 金色浅底胶囊 |
| 进阶 | Lv3–Lv4 | 金色实底胶囊 |
| 尊享 | Lv5 | 暖黑金底配金字 |

档位名称与 `VIP3` 格式的标识文案已确认。

组件只用样式，不加新图片资源。被主包页面（排行榜、我的）引用时体积可以忽略。

头像框素材的翼饰横向几乎铺满整图（框图外径约为头像直径的 1.625 倍），直接套在列表头像上会溢出布局盒并被 `overflow: hidden` 裁掉、压到相邻文字。组件因此提供三种占位方式，由各页面按周围空间选择：

- **默认**：布局盒就是头像本身，框图向外溢出。用于四周有空白的位置，如对局详情、结果页的双方卡。
- **`reserve-frame`**：布局盒按框预留（头像直径的 1.29 倍，与「我的」页一致），会员与非会员占位一致，列表行头像不会因是否有框而错位。用于排行榜、好友、首页摘要、对局中。
- **`fit-frame`**：传入的尺寸视为含框总占位，有框时头像缩进框内。用于领奖台这类空间固定的位置。此时没有框的头像保持原大小，并可用 `ring-color` 保留原有色环；有框时框本身就是环，不再叠加。

约球邀请卡与等待页没有段位数据，只传 `vip_level`，所以只有 VIP 标识、没有头像框。

观战与历史对局使用的公开详情接口（`PublicMatchDetailData`）不带会员字段，这些页面按非会员展示，本期不扩展。

### D6：表现分算法放在 `internal/ranking`，读取放在会员 logic

**算法。** 在 `backend/internal/ranking/performance.go` 新增纯函数 `PerformanceRating(samples []PerformanceSample, minSamples int) (rating int, bound Bound, ok bool)`，直接复用 `RackWinProbability` 与 `RaceWinProbability`，保证与结算公式一致。

- 求解方式：期望胜场对 R 单调递增，在整数分上二分，找到刚好达到目标的最小分后，取离目标更近的整数。下界为 0（与排位分下限一致），上界起点为最高对手分 + 3000，不够时按 3000 向外扩展。
- 全胜、全负：按 ΣS ∓ 0.5 求解，并返回 `bound`（至少 / 至多）。
- 样本少于 `minSamples` 场：返回 `ok = false`。90 天摘要用 `MinPerformanceSamples`（5），单月用 `MinMonthlyPerformanceSamples`（3）。
- 结果不小于 0：对手分很低又全负，或样本很多只赢极少场时，原始解会为负，展示时夹到 0。

**接口。** 新增 `GET /api/member/performance?game_type=`。

**读取计划。** 所有查询都有界：

1. 按 `idx_user_effective_at` 读取本人 `change_type = match_result`、该球种的记录，倒序，上限 600 行（`model.MaxAnalysisRankChangeRows`），只取分析需要的列。会员读取最近 6 个自然月（业务时区）；非会员只需要 90 天样本数与本月预览，读取最近 90 天。在 Go 中解析 `remark`：
   - 只有 V2 记录（`v = 2`）有意义，旧规则记录完全忽略。
   - `rated` 为真的 V2 记录进入样本；不计分的 V2 记录不进样本，但它的结算后分数仍可作为月末排位分。
2. 用本批 match id 一次 `IN` 查询对手同场记录的 `before_score`（`idx_match_id`）。对手记录缺失的样本（例如对手账号已注销清理）不计入，并记录数量。同一次查询还返回对手的用户 id。
3. 最佳胜利与爆冷失利的对手昵称和头像，用第 2 步得到的对手用户 id 批量读取 `users`（最多 2 个）。对手资料读取不到时昵称显示为「对手」，不影响分析结果。

**计算口径。**

- 摘要：取 90 天内最近 200 场。
- 实力曲线：用全部 6 个月数据，按月分组，每月少于 3 场时为空。
- 如果 600 行上限被触发，最早读到的记录所在月份及更早的月份标为不完整，且这些月份的表现分为空，避免用残缺样本给出错误的月度值。
- 月末排位分只取 V2 记录，旧规则的分数口径不同，不进入曲线。
- 查询次数固定：会员 4 次（用户、本人记录、对手赛前分、对手昵称），非会员 3 次，没有样本时少于这个数。

**锁定响应。** 第 1 步只读取 90 天、上限 200 行，返回：

- 90 天内的样本数（上限 200，客户端展示「200+」）。
- 本月表现分预览：只对本月（业务时区自然月）样本执行第 2 步并求解，口径与实力曲线的当月值相同。本月少于 3 场时为空，全胜或全负时带「至少 / 至多」标记。

锁定响应不返回期望胜场、90 天表现分、最佳胜利与爆冷失利、实力曲线或任何单场明细。

**响应字段。** 契约见 `backend/chasing_points.api` 中的 `GetMemberPerformanceResp`：

- `locked`、`sample_count` 在两种状态下都返回。
- 锁定时只多返回 `month_preview`。会员才返回 `summary`、`best_win`、`worst_loss`、`months`。
- 表现分用 `PerformanceRating`：`rating` 为数值，`bound` 为 `at_least` / `at_most` / 缺省（精确值）。样本不足时整个 `rating` 为 null。

**缓存。** 不加服务端缓存。`shared-read-caching` 要求用户派生数据首期读取数据库快照，有性能证据后才加用户级 Redis。客户端 Store 按 `userId + authGeneration + gameType` 缓存，对局结算后通过现有用户数据失效 scope 刷新。

### D7：单场复盘用纯函数按球种生成，视角与对局详情一致

**接口。** 新增 `GET /api/member/match-replay?match_id=`。

**门禁顺序。**

1. 对局存在、已完成，并且当前用户是双方之一。不满足时与无权访问的私有对局采用同一拒绝语义。
2. 当前用户是有效会员。不是会员时返回锁定状态和局数。

**数据读取。** 先统计该场动作数，超过 5000 条时不再读取动作，只返回局级数据并带 `detail_truncated`；否则按 `match_id` 读取已完成的局记录和 `is_undone = 0` 的动作，按局号、id 排序。只保留 `score/foul/win` 与斯诺克击球和局动作，开局、撤销、结束确认等流程动作全部剔除。不使用已完成对局的核心缓存，避免把一场的全部动作长期缓存。

**局记录的比分口径。** 斯诺克的局记录保存本局比分；其余球种保存「本局结束后的累计比分」，所以单局得分由相邻两局相减得到。

**生成。** 纯函数 `BuildMatchReplay` 放在 `backend/internal/logic/match_replay.go`，按球种分支：

- **斯诺克 V2：** 按 (局, 执行方, `visit_no`) 汇总得分，得到单杆。击球得分记给执行方，犯规罚分记给对方，犯规次数与罚分记在犯规方。
- **九球追分：** `score` / `win` 的得分记给执行方，`foul` 的罚分记给对方。同一方不间断的连续得分记为一段，对手得分会打断。
- **中八、美九：** 逐局 `win` 序列、最长连胜、`win_type` 统计，没有逐动作明细。
- **旧斯诺克（无事件）：** 只出局级数据。
- **宁缺勿错：** 某一局的动作累计出的比分与局记录对不上，或事件无法解析、V2 对局里混入旧版动作时，只丢弃这一局的明细，局级数据保留。

**响应字段。** 契约见 `GetMemberMatchReplayResp`：

- `locked`、`frame_count` 总是返回。会员才返回 `summary` 与 `frames`。
- `frame_only` 为 true 表示本该有逐动作明细（斯诺克、九球追分）但没有一局能给出明细：旧斯诺克对局、动作超出上限或明细全部损坏。中八、美九本来就是局级数据，不算降级。`detail_truncated` 只在动作超出上限时为 true。
- `my_max_run` / `opponent_max_run` 是同一个字段对两种球种的统一命名：斯诺克为本局单杆最高，九球追分为最大连续得分。中式八球、美式九球与旧斯诺克不返回。
- 中式八球、美式九球的每个 `frame` 是一局，`my_score` / `opponent_score` 是该局新增的得分（赢下的一方为 1），不返回 `trend`。逐局胜负序列由 `frames` 的 `winner` 组成，最长连胜与胜局方式统计在 `summary`。
- `my_foul_points` 是本方犯规送给对手的罚分。
- `key_tags` 取值 `decider`（决胜局）与 `comeback`（胜方落后分差最大）。

**走势降采样。** 走势只在得分变化处取点，`step` 是第几次得分变化。保留首点、末点与领先差的最大和最小点，其余按等间隔补足，每局最多 60 个点。降采样后 `step` 不再连续。

**视角。** 与 `MatchDetailData.is_player1` 一致，统一转换成「我 / 对手」。

**上限。** 一场的动作超过 5000 条时只返回局级数据，并带 `detail_truncated` 标记，防止异常数据拖慢接口。

**缓存。** 本期不加服务端缓存，只是单场有界读取（对局、用户、局记录、动作数、动作各 1 次；锁定时只有 3 次）。规格允许以后按 match id 与核心版本在门禁之后缓存。

## Risks / Trade-offs

- **[风险] 用户把 VIP 标识误解为「付费更强」。** → 标识只表示身份，档位来自对局积累的成长等级而不是充值金额。会员中心与锁定页明确写出「不影响排位分」。规格把排位不受影响写成可测要求。
- **[风险] 表现分与排位分并存造成困惑。** → 页面固定说明「表现分只反映这段时间打出的水平，不改变排位分」。样本少于 5 场不出数，单月少于 3 场不出数，减少小样本噪声。
- **[风险] 复盘遇到历史脏数据。** 例如旧斯诺克、撤销链、局号跳号。→ 构建函数按「宁缺勿错」降级到局级数据。测试覆盖撤销、旧斯诺克、超长对局与缺时间戳的情况。
- **[取舍] 排行榜会员标识最多延迟 20 秒。** → 规格已明确接受一个缓存周期的延迟，不为此增加失效链路。
- **[取舍] 合规模式下会员只能靠发放获得，短期内会员很少，权益价值难以用付费数据验证。** → 可以用常玩球馆奖励等现有发放途径先让一批用户体验，观察分析页的使用情况。
- **[风险] 主包体积。** → 新页面都在分包。新组件只用样式，头像框继续走 CDN。实现后用 HBuilderX 发行包核对主包体积。
- **[风险] 锁定入口让免费用户觉得被推销。** → 入口只放在竞技分析、对局结果这类自然位置，不弹窗、不加角标。免费用户原有的分析和海报一项都不减少。

## Open Questions

- 不提供隐藏 VIP 身份的开关，有效会员始终展示。
- 档位名称用「标准 / 进阶 / 尊享」，标识文案用 `VIP3` 这种格式。

- 成长规则：各级门槛 10/40/120/300，每日上限 8。
  - 依据：成长值不区分对手，每日上限是防刷的唯一限制，所以只小幅放宽，主要降低门槛。

  - 代码默认值、客户端与后台兜底常量已同步。已保存在数据库里的后台配置不受默认值影响，需要单独核对。
