## Context

移动端目前在主页、对局、排行榜和我的页分别打开同一个 `gameTypeModal`，该组件每次关闭都会清空选择。项目已有按用户 ID 生成本地存储键的做法，但没有对局偏好领域。斯诺克规则版本2在创建时要求正奇数 `best_of_frames` 和 `starting_actor`，后端通过 `best_of_frames / 2 + 1` 计算目标胜局并在达到目标后自动结算。

本变更跨越移动端偏好与 UI、API 契约、数据库模型、斯诺克写入状态机、排位结束确认和 WebSocket 快照。实现必须保留旧客户端、存量斯诺克对局和非斯诺克球种行为。

## Goals / Non-Goals

**Goals:**

- 让登录用户设置、修改或清除默认球种，并在所有发起 PK 入口打开 Modal 时得到一致预选。
- 保持“发起 PK → 选择球种 → 现有后续流程”的交互，不新增快速开始或跳过 Modal。
- 让新斯诺克对局默认使用自由局数，并在未记分时可切换为抢1～25局。
- 让自由局数支持局间正常结束、允许平局并限制最多49个已完成局。
- 让抢 N 局在任一方达到目标胜局时进入现有的正常结束流程。
- 让练习赛和排位赛共享赛制规则，同时保留排位赛结束确认。
- 通过新增字段保留旧 `best_of_frames` 语义，避免同一字段表达两种含义。

**Non-Goals:**

- 不新增“快速开始”按钮，不直接跳过球种 Modal 或扫码前确认。
- 不同步默认球种到服务端或跨设备；本期只做按用户隔离的本地偏好。
- 不允许对局开始记分后修改赛制。
- 不在本变更中删除斯诺克击球方、上手或开球方状态机；新建灵活赛制对局仅隐藏开局选择并使用兼容默认值。
- 不改变其他球种的记分、局数或结算规则。

## Decisions

### 1. 默认球种使用按用户 ID 隔离的本地偏好

新增轻量 `utils/game-type-preference.js`，通过 `default-game-type:<userId>` 读写 `uni` storage，并只接受 `GAME_TYPE_OPTIONS` 中的有效值。四个发起入口和设置页复用该 helper，不新增仅服务单字段的 Pinia store。

选择本地偏好而不是后端字段，是因为该配置只优化当前设备的发起流程，不影响服务端业务真相。按用户 ID 分键可避免切号串用；读取到无效值时视为“每次询问”。

`gameTypeModal` 接收 `defaultType`，每次打开时以有效默认值初始化选择；没有默认值时保持未选择。Modal 显示“默认”标记和“将当前选择设为默认”控制。确认事件携带本次球种及是否更新默认值；临时选择其他球种时默认不改写偏好。设置页提供“每次询问”作为清除入口。

### 2. 发起 PK 的现有入口和后续流程保持不变

所有现有按钮继续显示“发起 PK”并打开 Modal。默认值只减少重复点选，不改变扫码、出示二维码、好友选择、练习赛/排位赛、公开范围、进行中对局拦截和页面导航。斯诺克确认后不再调用开局赛制 action sheet，而是按自由局数创建并继续现有扫码流程。

### 3. 新赛制使用独立字段，不复用 `best_of_frames`

`matches` 新增：

- `snooker_format`: `legacy`、`free` 或 `race_to`。
- `snooker_target_wins`: 自由局数为0，抢 N 局为1～25。

保留 `best_of_frames` 用于旧客户端和存量对局。迁移将已有规则版本2且 `best_of_frames > 0` 的记录标记为 `race_to`，并把目标胜局回填为 `best_of_frames / 2 + 1`，从而保持原结束阈值；其他存量记录保持 `legacy`。

新客户端创建规则版本2斯诺克时显式提交 `snooker_format=free`、`snooker_target_wins=0`。为兼容现有详细规则状态机，未提交开球方时服务端暂用选手1作为内部初始值；客户端不再展示开球方选择。旧客户端显式提交 `best_of_frames` 时继续按旧语义创建并映射到等价目标胜局。

### 4. 赛制只允许在第一条记分动作前修改

新增认证接口更新斯诺克赛制，请求包含 `match_id`、`snooker_format`、`snooker_target_wins` 和 `base_revision`。服务端事务锁定对局，并要求：

- 当前用户是对局创建者；
- 对局状态为进行中且没有结束确认；
- 未绑定裁判；
- 不存在 `match_actions` 和 `match_rounds`。

更新只修改对局配置并递增 revision，不写入记分动作，因此创建者可以在首次记分前再次调整。成功后广播包含新赛制和 `can_change_snooker_format` 的权威同步快照。若修改与首个记分动作并发，行锁和 base revision 确保只接受一个顺序，客户端以返回快照收敛。

移动端在斯诺克记分页展示赛制行。可修改时点击“自由局数”或“抢 N 局制”原地展开滚动选择器；N 范围1～25，并显示“最多可能进行 2N-1 局”。锁定后移除箭头和交互态，不通过弹窗告知禁止修改。

### 5. 自由局数按已完成局结算

自由局数不在单局结束后按胜局数自动完成整场。只有满足以下条件时显示正常“结束整场对局”操作：

- 至少存在一个 `match_rounds`；
- 当前局已经结算，`current_frame_started=false`；
- 对局仍可正常结束。

正常结束使用实际已完成局形成的整场比分，允许平局。0局退出继续走取消对局，不生成正式战绩。完成第49局后服务端自动触发正常结束条件，并阻止开始第50局。

### 6. 抢 N 局按目标胜局结束

抢 N 局直接使用 `snooker_target_wins`，不再通过总局数换算。任一方达到 N 胜后阻止开始下一局，并进入正常结束流程；理论最大局数为 `2N-1`，N 最大25，因此不会超过49局。

固定赛制不展示自由局数的“结束整场对局”按钮。提前停止仍使用已有认输、取消或裁判判罚路径，不把未达到目标的停止记录为正常完赛。

### 7. 排位赛复用赛制，但保留结束确认

练习赛达到正常结束条件后直接结算。排位赛无论由自由局数按钮、49局上限或抢 N 目标触发，都冻结比分并进入现有 `pending_confirmation` 流程；对手确认后才完成竞技结算，异议后恢复记分。平局是自由局数的合法结果，沿用现有平局结算能力。

### 8. 契约和快照统一暴露赛制状态

创建响应、当前对局、详情、同步快照、公开详情和 WebSocket 数据统一增加 `snooker_format`、`snooker_target_wins`、`can_change_snooker_format`。移动端只以服务端快照决定赛制、目标和可修改状态，不依据本地比分猜测。

## Risks / Trade-offs

- [旧客户端不理解自由局数] → 旧客户端未提交新字段时继续走 legacy 创建；新字段只由新客户端启用，响应保留旧字段。
- [数据库同时保留两个赛制字段容易混淆] → 将 `best_of_frames` 明确限定为兼容字段，新逻辑只读取规范化后的 format/target helper，并补迁移与兼容测试。
- [排位达到目标时自动结算会绕过确认] → 统一通过正常结束协调器，根据 `match_mode` 选择直接结算或进入 `pending_confirmation`。
- [赛制更新与首次记分竞争] → 同一事务中锁定 match、校验 base revision 和动作/局记录，失败时返回最新快照。
- [自由局数长期不结束] → 服务端限制最多49个已完成局，达到上限后禁止继续并触发正常结束。
- [本地默认球种不跨设备] → 本期明确为设备偏好；若后续需要账号同步，再迁移为服务端用户偏好，不提前扩展接口。

## Migration Plan

1. 新增兼容迁移，先通过 `information_schema.COLUMNS` 判断字段是否存在，再添加 `snooker_format` 和 `snooker_target_wins`。
2. 将已有规则版本2且总局数有效的斯诺克记录回填为 `race_to` 和等价目标胜局，其余存量记录保持 `legacy`。
3. 更新 `.api` 后立即运行 goctl，随后实现模型、逻辑、快照和 WebSocket；先部署兼容新旧请求的后端。
4. 部署移动端，新建对局开始显式使用自由局数和默认球种偏好。
5. 回滚移动端不会破坏后端；若必须回滚后端，应先停止创建灵活赛制对局并确认没有进行中的 `free`/`race_to` 新格式对局，避免旧后端误解释新记录。

## Open Questions

无。产品规则已确定为：自由局数允许平局且最多49局，抢 N 的 N 范围1～25，练习赛和排位赛共享赛制，排位继续结束确认。
