未执行：鸿蒙编译（`UNI_PLATFORM=app-harmony`）。

主要回归测试覆盖：

- 得分构成构建函数：完整对局统计、最后一次胜局之后的犯规、撤销动作、旧胜法代码、早期 `score` 动作、未知胜法、`extra_data` 缺失回退到局记录、对账失败降级、明细超过 200 条截断、非九球追分返回空。
- 详情接口：参与者详情与公开详情（进行中 / 已完成）返回得分构成；选手 2 请求时固定位置不交换；中式八球不返回；公开详情九球追分比中式八球恰好多 2 条查询。
- 总结与复盘：九球追分总结条目不再含本人胜法次数；复盘为单个整场片段，含尾部犯规、选手 2 视角、对账失败与超长降级、撤销动作；中式八球、美式九球、斯诺克复盘用例原样通过。
- UniApp：得分构成展示模型（视角换边、中立视角、犯规文案、倒序、降级）；详情归一化（公开详情按 `perspective_user_id`、参与者详情按 `is_player1`、裁判中立）；详情页静默刷新（防抖、失败静默、迟到响应丢弃、对局结束再刷新）；结算页与复盘页挂载；记分页九球追分不显示"第 N 局"。

## 2. 生产数据只读抽样（任务 1.0）

环境：生产库，经 `ssh chasingpoints-prod` 在服务器本机执行，只读事务，仅 `SELECT` 聚合，未写入任何数据，未输出凭据。执行前已获用户确认。

结果：已完成的九球追分对局共 1 场（创建于 2026-10-27）；按有效动作累计的双方总分与最终比分一致；24 个胜局动作的胜法与分值全部为普胜 4 / 小金 7 / 大金 10；1 次犯规，分值 1；没有 `score` 动作；胜局动作都带 `extra_data` 且都有对应局记录。

结论：2026-10-13 记分校验修复之前的存量九球追分对局在生产上不存在，降级方案无需调整。

## 3. H5 渲染目检（模拟接口）

方式：H5 开发构建 + 本机模拟接口（HTTPS，自签证书）+ 无头 Chrome 截图，窗口宽 500。接口域名全部映射到本机，请求日志确认没有请求到达真实后端。数据为手工构造的一场 18:15 九球追分对局，**不是真实后端响应，不代表后端验收**。

| 场景 | 结果 |
| --- | --- |
| 详情页，观战视角（公开详情） | 对照表标题为"选手1 / 选手2"，6 行数字与构造数据一致；得分明细 9 条倒序；不出现"总局数""当前局""局记录" |
| 详情页，观战视角，深色（在页面根节点注入 `dark-mode` 类） | 卡片、表格、明细条目的底色与文字对比正常 |
| 详情页，选手 2 本人（参与者详情） | 对照表标题为"我 / 对手"，左右与头部比分一致 |
| 详情页，得分构成不可用 | 只显示总分一行与"记分明细暂不可用"提示 |
| 详情页，中式八球 | 仍显示"总局数 / 当前局 / 局记录"，与改动前一致 |
| 结算页，选手 2 本人，浅色与深色 | "得分构成"卡片位于"本场数据"之前；"本场数据"不再重复胜法次数 |
| 复盘页，会员 | 整场数据对照 + 单个"整场走势"片段；不出现"第 N 局""赢下局数""共 N 局" |
| 复盘页，锁定 | 文案为整场口径，不显示局数 |

H5 的已知限制：`uni` API 被摇树导致主题同步报错、深色模式需手工注入类名，图标颜色等仍需在微信开发者工具或真机确认。

目检后做了两处文案调整（已有单元测试覆盖，未重新截图）：犯规条目的分值前写明得分方；复盘片段不再重复"最大连续得分"。

## 5. 与设计的偏离

- 会员复盘响应新增可选字段 `viewer_actor`（查看者是选手 1 还是选手 2）。得分构成固定按选手 1 / 选手 2 返回，而复盘其余数据是"我 / 对手"视角，客户端需要它来对齐两者。
- 参与者详情与已完成对局的公开详情，用已加载的有效动作数判断是否超过 5000 条（不新增查询）；进行中对局的公开详情按动作总数（含已撤销）计数。两者只在动作数恰好跨过阈值时有差别。
