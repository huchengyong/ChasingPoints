# 上传球馆基础资料收口设计

## 背景

当前「上传球馆」页面不是一个轻量提交入口，而是一个偏完整的资料采集表单。页面中除了基础资料外，还包含：

- 位置与联系
- 经营信息
- 特色说明

对应字段包括联系电话、营业时间、球桌数量、台费范围、球馆简介等。前端 `app/subPages/venue/submit.vue` 会把这些字段一并提交给 `/api/venue/create`，后端 `CreateVenueReq` 也仍然对这些字段开放。

这会带来两个问题：

- 页面心智负担偏高，用户在提交一个新球馆时需要面对太多非必要信息
- 前后端都默认“上传球馆需要尽量填全”，而不是“先用最小资料建档，其他资料后续再补”

## 目标

- 把上传球馆收缩为一个最小可提交入口。
- 页面只保留“基础资料”，减少新球馆创建时的填写负担。
- 让前端表单结构、接口入参和后端校验保持一致，不留下“页面删了但接口还在收”的灰区。
- 保持已有异步定位与待审核流程不变。

## 非目标

本次不包含以下范围：

- 不修改球馆数据库表结构
- 不重写异步地理解析流程
- 不调整球馆列表与详情接口的返回字段
- 不新增后续补充资料的编辑入口
- 不对球馆详情页做大规模结构重设计

## 设计结论

本次采用“前后端同步收口”的方案：

- 前端上传页只保留一个“基础资料”区块
- 创建接口只接收基础资料相关字段
- 其余数据库字段在后端创建时继续写默认空值

这不是“视觉隐藏字段”，而是“输入面真实收缩”。

## 字段范围

### 保留字段

- `name`：球馆名称，必填
- `city`：城市，必填
- `district`：区域，选填
- `address`：详细地址，必填

### 移除字段

- `phone`
- `images`
- `business_hours`
- `table_count`
- `price_range`
- `description`

其中 `district` 仍然建议保留，因为它能帮助生成更准确的 `full_address`，同时对用户来说填写成本很低。

## 前端页面设计

### 页面结构

上传页只保留一个“基础资料”表单区块，包含：

- 球馆名称
- 城市
- 区域
- 详细地址

原来的以下内容全部移除：

- 位置与联系区块
- 联系电话输入框
- 经营信息区块
- 特色说明区块

### 引导文案

页面文案需要同步从“尽量补充完整资料”改成“先提交基础资料即可”。

建议调整为：

- 页面标题保留 `完善球馆信息`
- 页面说明改成：`填写基础资料后即可提交，系统会根据地址自动定位球馆位置。`
- 基础资料区块提示改成：`请填写球馆名称、城市和详细地址，方便大家准确找到这里。`

### 提交区文案

提交栏文案不再出现“其他内容可以继续补充”这类描述，因为本次已经不再提供其他资料输入项。

建议改成：

- 完整前：`还有 X 项未填写`
- 完整后：`确认基础资料后上传球馆`
- 完整后副文案：`提交后系统会根据地址自动定位并等待审核。`

## 后端接口设计

### CreateVenueReq

`CreateVenueReq` 只保留以下字段：

- `name`
- `city`
- `district`
- `address`

这样接口语义与前端表单完全一致。

### 校验规则

继续保持当前最小校验：

- 球馆名称不能为空
- 城市不能为空
- 详细地址不能为空

`district` 继续为选填。

### 落库行为

后端仍然创建完整的 `model.Venue`，但与本次输入无关的字段统一保持默认值：

- `Phone = ""`
- `Images = "[]"`
- `BusinessHours = ""`
- `TableCount = 0`
- `PriceRange = ""`
- `Description = ""`

这样不需要改数据库结构，也不会影响现有详情页和列表页的数据读取逻辑。

## 影响范围

### 前端

- `app/subPages/venue/submit.vue`
- `app/api/venue.js`

### 后端

- `backend/chasing_points.api`
- `backend/internal/types/types.go`
- `backend/internal/logic/create_venue_logic.go`
- `backend/internal/logic/create_venue_logic_test.go`

## 测试策略

### 前端

验证上传页提交 payload 只包含基础资料字段，不再拼接联系电话、营业信息和简介。

### 后端

新增或更新单测，覆盖：

- 缺失基础资料时报错
- 只提供基础资料也能成功构建 `Venue` 和异步地理任务
- 被移除字段不再出现在 `CreateVenueReq` 的构建路径中

## 风险与取舍

- 球馆详情页短期内仍可能展示“暂未填写”的营业时间、简介等空态，这是可接受的，因为本次目标是收缩提交入口，不是重做展示页。
- 数据库表仍保留扩展字段，这是刻意保留的兼容层，避免这次改造牵扯 migration。
- 如果未来要恢复补充资料，建议通过“编辑球馆资料”而不是重新把创建页做回大表单。

## 推荐结论

这次最合适的落地方式，不是只删掉前端几个输入框，而是把“上传球馆”的能力重新定义为：

- 用最小基础资料建档
- 后续由系统先定位、审核
- 其余扩展信息以后再补

前后端同步收口后，这条链路会更轻，也更一致。
