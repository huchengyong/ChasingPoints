# 会员订阅与好友主页精简设计

## 背景

当前移动端在这三块存在明显割裂：

- `app/subPages/social/friendHomepage.vue` 仍在首屏展示“你和 TA”的关系摘要，好友主页没有真正聚焦“看对方”
- `app/pages/user/index.vue` 的 `隐藏战绩` 只写入本地存储，没有真实后端状态，属于假功能
- `app/pages/user/index.vue` 里现有会员相关展示主要围绕“上传球馆送会员”奖励状态，没有独立会员订阅入口，也没有真实支付链路

同时，仓库当前已经具备几个可复用前提：

- 后端 `users` 表已有 `member_expires_at` 字段，可承接订阅生效结果
- `backend/.env.example` 已预留支付宝、微信支付配置项
- `backend/go.mod` 已有 `github.com/go-pay/gopay` 依赖
- `PK 报表` 已经承载“我和好友之间的对比信息”，不需要继续塞进好友主页

## 目标

- 把好友主页精简成“纯好友信息 + 直接查看对方战绩列表”的页面
- 把“隐藏战绩”从前端假开关改成真实服务端隐私配置
- 在不影响现有“上传球馆领会员”奖励卡的前提下，新增真正的会员中心和 APP 端月卡订阅能力
- 打通 APP 端真实支付闭环：下单、拉起支付、异步回调、会员时长入账、状态回显
- 所有展示与业务结算时间统一按 `UTC+8` 处理

## 非目标

本次不包含以下范围：

- 小程序支付
- 多套餐订阅（季卡、年卡）
- 自动续费
- 管理后台会员运营页
- 官网会员介绍页
- 对“上传球馆送会员”奖励规则本身的改动

## 已确认约束

- 现有“领取会员”奖励卡必须保持现状，不改它的引导职责
- 会员订阅本次只做 `月卡`
- 先打通 `APP` 端支付
- 好友主页所有和“我”相关的数据全部去掉，双方对比只放在 `PK 报表`
- 如果目标用户隐藏战绩，好友主页战绩区显示 `对方已隐藏战绩`
- 时间统一为 `UTC+8`

## 方案对比

### 方案 A：只改前端结构，支付先占位

优点：

- 改动小
- 页面能先变得更合理

缺点：

- 会员订阅仍是假入口
- 与需求“直接对接上支付功能”不符

### 方案 B：最小真实支付闭环

做法：

- 好友主页精简
- 隐藏战绩改成真实服务端开关
- 新增会员中心页
- 后端新增会员套餐、订单、支付创建、支付回调、订单查询
- APP 端使用 `uni.requestPayment` 拉起支付宝 / 微信支付

优点：

- 范围可控
- 能把核心业务闭环真正跑通
- 后续扩套餐和补运营能力有明确基础

缺点：

- 需要同时改 `app/`、`backend/`、migration、API 契约

### 方案 C：完整会员体系一期全上

做法：

- 在方案 B 上继续加入订单列表、退款、自动续费、权益矩阵、支付补单后台

优点：

- 一次性能力更完整

缺点：

- 范围明显过大
- 风险高，超出当前需求

## 设计结论

采用 **方案 B：最小真实支付闭环**。

本次聚焦三个交付：

1. 好友主页从“关系页”收敛为“好友信息页”
2. 隐藏战绩从本地假状态变成真实后端隐私配置
3. 会员从“奖励展示”扩展为“奖励卡保留 + 独立会员中心 + APP 端月卡支付”

## 一、好友主页设计

### 页面定位

好友主页不再承担“我和 TA 的交锋摘要页”职责，而是承担：

- 识别这个好友是谁
- 给出进入 `PK 报表` 的快捷入口
- 直接展示对方自己的战绩列表或隐藏状态

### 页面结构

#### 1. Hero 好友名片

展示：

- 头像
- 昵称
- 用户 ID
- 段位
- `PK 报表` 按钮

去掉：

- `你暂时领先`
- `你们已经认真交手 X 场`
- `你 X 胜 Y 负`
- `最近一次交手`
- 所有“你们关系如何”的表述

#### 2. 战绩列表区

默认直接展示“对方战绩列表”，不再放“查看对方战绩”按钮作为二次跳转。

战绩区数据来源继续复用现有 `opponentRecord` 逻辑和后端 `/api/opponent/list` 能力，只是在好友主页里以内嵌列表方式展示。

#### 3. 隐藏态

当目标用户开启隐藏战绩时：

- 不展示战绩列表
- 改为固定空态：`对方已隐藏战绩`

#### 4. PK 报表

保留 Hero 内按钮进入 `app/subPages/social/pkReport.vue`。

职责保持不变：

- 只在这里看“我和好友”的对比信息
- 不把这种信息再塞回好友主页

## 二、隐藏战绩设计

### 当前问题

`app/pages/user/index.vue` 中的 `隐藏战绩` 当前只写本地存储 `user_hide_match`，没有任何后端真状态，也不会影响实际接口返回。

### 目标行为

- 用户在“我的”页打开或关闭隐藏战绩
- 状态写入服务端，并在设备切换后仍可回显
- 好友查看其“对方战绩”时受这个开关约束
- `PK 报表` 不受该开关影响

### 数据设计

在 `users` 表新增布尔字段，例如：

- `hide_match_record`：是否隐藏战绩，默认 `false`

### 接口设计

新增用户隐私接口：

- `GET /api/user/privacy`
- `POST /api/user/privacy`

返回至少包含：

- `hide_match_record`

### 权限规则

- 用户自己查看自己的对手记录、交锋记录，不受隐藏战绩限制
- 查看好友主页中的“对方战绩列表”时，如果目标用户开启隐藏，后端返回隐藏态，不返回明细
- 查看 `PK 报表` 时仍允许读取双方交锋数据

## 三、会员中心与支付设计

### 产品结构

#### 保持不动的部分

`app/pages/user/index.vue` 里现有“上传球馆送会员”奖励卡继续保留，不改文案定位和引导动作。

#### 新增部分

在“我的”页新增一个独立 `会员中心入口卡`：

- 未开通：显示 `月卡会员 · 立即开通`
- 生效中：显示 `会员有效期至 ... · 立即续费`
- 已到期：显示 `会员已到期 · 立即续费`

点击进入新页面：

- `app/subPages/user/memberCenter.vue`

### 会员中心页面内容

首期只做一个套餐：

- 月卡

展示内容：

- 当前会员状态
- 到期时间
- 月卡价格
- 订阅说明
- 支付方式切换：支付宝 / 微信支付
- `立即开通` / `立即续费` 按钮

### 后端能力

新增会员订阅域，至少提供：

- 套餐查询
- 创建会员订单
- 查询会员状态
- 查询单个订单支付状态
- 支付宝异步回调
- 微信支付异步回调

### 订单模型

新增会员订单表，至少包含：

- `order_no`
- `user_id`
- `plan_code`
- `plan_name`
- `amount_fen`
- `currency`
- `pay_channel`
- `status`
- `third_party_order_no`
- `paid_at`
- `member_expires_at_before`
- `member_expires_at_after`
- `created_at`
- `updated_at`

推荐状态：

- `pending`
- `paid`
- `closed`
- `failed`

### 套餐模型

首期可不单独建表，直接在服务端通过固定配置返回唯一月卡套餐；如果实现时考虑后续扩展，也可建立轻量套餐配置表。

本次更推荐先使用后端固定配置，避免额外运营复杂度。

### 支付流程

#### 1. 创建订单

前端在会员中心选择支付方式后，请求后端创建订单。

后端完成：

- 校验登录用户
- 校验套餐编码
- 生成业务订单号
- 落订单为 `pending`
- 根据支付方式调用对应 SDK 生成 APP 端拉起支付所需参数

#### 2. APP 端拉起支付

前端拿到支付参数后调用 `uni.requestPayment`：

- 支付宝使用 `provider: 'alipay'`
- 微信支付使用 `provider: 'wxpay'`

#### 3. 异步回调

后端仅以异步回调作为最终支付成功依据，不以前端支付成功弹窗作为准。

回调处理必须：

- 验签
- 幂等
- 校验订单金额和状态
- 更新订单为 `paid`
- 计算新的 `member_expires_at`
- 更新用户会员到期时间

#### 4. 到期顺延规则

- 若用户当前 `member_expires_at` 晚于“当前 UTC+8 时间”，则从原到期时间继续顺延 1 个月
- 若已过期或为空，则从当前 UTC+8 时间起生效 1 个月

### 支付安全要求

- 任何密钥、证书只从环境变量读取
- 回调必须验签
- 订单状态更新必须幂等
- 金额、商户号、应用 ID 必须与本地订单严格校验
- 前端不得自行决定会员是否到账

## 四、时间与时区设计

### 统一规则

所有用户可见时间统一按 `UTC+8` 处理。

适用范围：

- 会员到期时间展示
- 订单支付时间
- 订单创建时间
- 隐私状态更新时间（如后续需要）

### 后端策略

- 业务计算统一以 `UTC+8` 当前时间作为基准
- 接口返回给前端的时间字符串统一格式化为东八区时间字符串
- 支付回调里的第三方时间如为其他时区，入库前统一转换

### 前端策略

- 对会员状态、订单状态等关键时间，优先直接展示后端已格式化好的 `UTC+8` 字符串
- 避免再做一次本地时区换算，减少跨端偏差

## 六、验收标准

### 好友主页

- 好友主页首屏不再出现“我”和“对方”的比较数据
- Hero 卡只展示对方信息和 `PK 报表` 按钮
- 页面直接展示对方战绩列表
- 对方隐藏战绩时，列表区显示 `对方已隐藏战绩`

### 隐藏战绩

- “我的”页开关切换后刷新仍能回显
- 更换设备登录后状态仍一致
- 好友主页查看战绩时受该开关约束
- `PK 报表` 不受影响

### 会员订阅

- “我的”页能进入独立会员中心
- 月卡订单可以成功创建
- APP 端能成功拉起支付宝 / 微信支付
- 支付回调成功后会员到期时间正确顺延
- 已有会员再次购买时按现有到期时间顺延
- 所有时间展示为 `UTC+8`

## 七、风险与注意事项

- `backend/.env.example` 目前应用名和数据库名仍是旧值，接支付时要只复用支付配置项，不要误把其他旧示例当当前事实
- `goctl` 生成代码后不得手改生成文件
- 支付回调测试依赖真实签名和参数结构，单元测试里要优先覆盖幂等与过期时间计算纯逻辑
- APP 端 `uni.requestPayment` 参数结构按渠道不同而不同，前端需要保持接口返回字段与渠道一一对应
