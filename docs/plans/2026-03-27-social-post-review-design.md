# 动态发布审核设计

## 背景

当前动态模块的真实行为是：

- 用户发布动态后直接写入 `social_posts`
- 广场流和关注流直接读取 `social_posts`
- 动态表没有审核状态、拒绝原因、审核记录等字段
- 管理后台没有动态审核入口

这意味着只要用户能发动态，内容就会直接进入公开流。对社区型内容来说，这会带来比较直接的治理风险：

- 辱骂、挑衅、诈骗引流等内容可能直接暴露给其他用户
- 敏感或违法违规内容缺少前置拦截
- 平台缺少明确的审核与处置闭环

同时，纯粹把“发帖成功”改成“发完就消失，等审核再说”也会让用户体验明显变差，容易产生“是不是没发出去”的困惑。

## 目标

- 为动态发布链路增加最小可用的审核机制。
- 确保待审核内容不会进入公开广场、关注流、首页精选等公开曝光场景。
- 让作者能够在独立的“我的动态”中查看自己内容的审核状态，避免“发完消失”。
- 支持后台对动态进行通过/拒绝审核，并在拒绝时填写原因。
- 为后续接入举报、敏感词、机审、禁言等治理能力预留清晰扩展点。

## 非目标

本次不包含以下范围：

- 接入第三方文本/图片机审服务
- 新增举报、申诉、禁言、封号等治理机制
- 动态编辑后重新提交审核
- 动态详情页、分享页、搜索结果等内容场景扩展
- 复杂的分级放行策略，例如老用户直发、新用户待审

## 方案对比

### 方案 A：全部待审核，作者不可见

做法：

- 用户发布后状态为待审核
- 作者和其他人都看不到，直到审核通过

优点：

- 逻辑简单
- 风险最低

缺点：

- 用户体验差
- 用户容易误以为发帖失败或丢失

### 方案 B：作者在公开流中“假公开”自见

做法：

- 用户发布后状态仍为待审核
- 作者在广场里仍然看到自己的内容，看起来像已经公开
- 实际其他人看不到

优点：

- 作者侧几乎无感

缺点：

- 容易形成“影子公开”的错觉
- 一旦用户发现他人不可见，平台信任风险较高
- 审核状态不透明，不利于长期治理

### 方案 C：新增“我的动态”，作者在私有列表中自见

做法：

- 用户发布后状态为待审核
- 公开流只展示已发布内容
- 作者在“我的动态”中能看到自己的全部动态和审核状态

优点：

- 体验和治理比较平衡
- 不制造“已经公开”的误导
- 拒绝原因和状态有稳定承载位置

缺点：

- 需要新增一条作者私有视图链路

## 设计结论

本次采用 **方案 C：新增“我的动态”，作者在私有列表中自见**。

核心原则：

- `公开场景` 只展示审核通过的动态
- `作者私有场景` 展示自己的全部动态及审核状态
- `拒绝结果` 对作者透明，可见拒绝原因

这样既能避免公开流裸发，又不会让作者觉得内容消失了。

## 状态设计

动态状态收敛为 3 个值：

- `1 = 已发布`
- `2 = 待审核`
- `3 = 已拒绝`

新增字段：

- `status`：审核状态，默认 `2`
- `reject_reason`：拒绝原因，默认空字符串
- `reviewed_at`：审核时间，可空
- `reviewed_by`：审核管理员 ID，可空

字段设计意图：

- `status` 用于所有读写过滤的唯一审核状态口径
- `reject_reason` 用于作者可见的审核反馈
- `reviewed_at / reviewed_by` 用于运营留痕与后台排查

## 数据流设计

### 用户发布

发布动态后：

1. 服务端写入 `social_posts`
2. 默认状态设为 `待审核`
3. 返回发布成功
4. 前端提示“已提交审核，可在我的动态查看进度”

### 公开读取

以下场景只读取 `已发布` 动态：

- 广场流
- 关注流
- 首页精选动态
- 未来的搜索、分享、推荐等公开分发位

### 作者私有读取

新增“我的动态”接口，只返回当前登录用户自己的动态：

- `待审核`：作者可见，展示“审核中，仅自己可见”
- `已发布`：作者可见，正常展示
- `已拒绝`：作者可见，展示“审核未通过”与拒绝原因

## API 设计

### 用户侧接口

保留现有接口语义：

- `POST /api/social/post`
- `GET /api/social/public`
- `GET /api/social/feed`

新增接口：

- `GET /api/social/mine`

其中：

- `public/feed` 只返回 `status = 已发布`
- `mine` 返回当前用户自己的全部动态，并补充状态字段

### 管理侧接口

新增动态审核管理接口：

- `GET /api/admin/social/posts`
- `POST /api/admin/social/review`

管理列表支持按状态筛选，审核操作支持：

- 通过
- 拒绝

当审核拒绝时：

- `reject_reason` 必填

## 前端交互设计

### 发布页

发布成功提示改为：

- `已提交审核，可在“我的动态”查看进度`

本次不做“审核中即显示在公开流”。

### 我的动态

新增作者私有列表页，承载三类状态：

- `审核中，仅自己可见`
- `已发布`
- `审核未通过`

若为拒绝状态，卡片内直接展示拒绝原因。

作者可删除自己的：

- 待审核动态
- 已拒绝动态
- 已发布动态

本次不做“编辑后重新提交”。

### 用户入口

在用户“我的”页新增“我的动态”入口，作为审核状态的唯一稳定承载位置。

## 管理后台设计

新增“动态审核”模块，和现有球馆审核风格保持一致。

列表能力：

- 按状态筛选：全部 / 待审核 / 已发布 / 已拒绝
- 展示发布人、内容摘要、图片数量、动态类型、发布时间、状态

详情能力：

- 查看全文
- 预览图片
- 查看拒绝原因

操作能力：

- 审核通过
- 审核拒绝

审核拒绝时要求填写拒绝原因，便于作者理解和后续申诉扩展。

## 边界规则

以下规则在本次实现中固定：

- 非 `已发布` 动态不得进入公开流
- 非 `已发布` 动态不得被其他用户点赞、评论、查看评论
- 作者只能通过“我的动态”看到待审核或已拒绝内容
- 审核通过后动态沿用原始 `created_at`，不改排序时间
- 审核拒绝后动态继续保留在“我的动态”中，并显示拒绝原因
- 拒绝原因只对作者和管理员可见

## 合规与产品判断

本方案的核心是“作者可见，但仅限私有列表且明确标注审核状态”，而不是“作者误以为已经公开”。

这样做的产品和治理判断是：

- 用户体验上避免“内容消失”
- 平台表达上不制造“假公开”错觉
- 审核状态透明，拒绝原因可追溯

这是比“完全无感自见”更稳妥的实现方式。

## 测试要求

后端至少覆盖：

- 新发动态默认 `待审核`
- 公开流 / 关注流仅返回 `已发布`
- 我的动态返回作者自己的三种状态
- 审核拒绝必须填写拒绝原因
- 非 `已发布` 动态不能点赞评论

前端至少覆盖：

- 发布成功文案变更
- 我的动态状态文案展示正确
- 拒绝原因可见

管理端至少覆盖：

- 动态审核列表可按状态筛选
- 审核通过 / 审核拒绝操作可用
